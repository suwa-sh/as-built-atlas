# ui-nextjs プロファイル: エージェント向けの説明

対象は「Next.js で作った、画面を持つシステム」。画面と API とデータの読み書きが同じリポジトリにあるもの。入口の発見と入口ごとの分析で、このファイルと `profile.yaml` の両方を読む。

App Router (`app/`) を前提に書いている。Pages Router (`pages/`) の画面がある (両方が同居する、移行の途中のものも) ときは、下の「Pages Router の画面」の節も読む。そこに書いていないことは、App Router と同じ。

## アーキテクチャと層の連鎖

```text
page (app/**/page.tsx。URL 1 つ = 画面 1 つ)
  → component (React コンポーネントと、API を呼ぶフック。ブラウザ側で動くことが多い)
    ⇢ api_route (ブラウザ側からサーバー側へ入る口。2 種類ある)
        ・route ファイルの GET / POST … (HTTP をはさむので、関数の呼び出しではなく URL でつながる)
        ・'use server' の関数 (Server Function)。import して呼ぶので、定義へそのまま辿れる
      → query (サーバー側の関数: 問い合わせ、認証・権限の検査、共通の lib)
        → external (ORM・DB クライアント・キャッシュ・メッセージ基盤。ここで終端)
```

- `page` と `layout` が `role: entry`。page ファイル 1 つ = 入口 1 件、layout ファイル 1 つ = 入口 1 件
- `part` も `role: entry`。登録表から選ばれて描かれる部品を、画面とは別の入口に分けたときだけ使う (下の「登録表から選ばれて描かれる部品」)。連鎖の先頭が `part` に替わるだけで、その先は同じ
- `layout` (画面を包む共通の枠) は、連鎖の先頭が `layout` に替わるだけで、その先は同じ (`layout → component ⇢ api_route → query → external`)。画面と枠は**別々に分析する** (下の「画面と、画面を包む枠」)
- `external` が `role: boundary`。ライブラリ・SDK の呼び出しに達したらコールスタックを閉じる
- サーバー側で動く page やコンポーネント (ファイルの先頭に `'use client'` が無く、`'use client'` のファイルから import されてもいないもの) が、API を通さずにサーバー側の関数を直接呼ぶ書き方もある。そのときは `page` / `component` から `query` へ直接つなぐ (`api_route` を作らない)
- page やコンポーネントのファイルに ORM の呼び出しや SQL、サーバー側の `fetch` が直接書いてあるときは、そのフレームの `io` に書く (`page` と `component` もデータの種類を持てる)。その呼び出しが届くライブラリを `external` フレームにして閉じる

## 入口の判別 (抽出器のパラメータの決め方)

- app ディレクトリの場所を確かめる (`src/app` か `app`)。`files`・`exclude`・`segments.strip_prefix` を同じ場所にする
- 階層パスは URL の形。`(group)` は URL に出ないので落とす。`[id]` (動的な段) と `@slot` (並行ルート) は残す
- 一覧の上に小窓で重ねる画面 (並行ルート + 割り込みルート、例 `@modal/(.)photos/[id]`) は、同じ URL の通常の画面とは別の入口として列挙する。段に `@modal` が残るので区別できる
  - この入口の階層パスは、割り込み先の URL ではなく**置き場** (どの画面の上に重なるか) を表す。`(..)` や `(...)` は「1 つ上」「ルート」の URL を割り込むという意味なので、表す URL は階層パスと違うことがある (例: `feed/@modal/(..)photo/[id]` は `/feed` の上に重なり、URL は `/photo/[id]`)。割り込み先は entry の `attributes.file_segments` (加工前の段) で確かめ、入口の `summary` に「どの URL を、どの画面の上に重ねて出すか」を書く
- 入口の id は階層パスから記号を除いたもの。段の種類は「`_` + 1 文字」の印で表す: `[id]` → `id_d`、`[...path]` → `path_c`、`[[...path]]` → `path_o`、`@modal` → `modal_s`、app 直下の page → `root_r` (例: `/websites/[websiteId]/sessions` → `websites.websiteId_d.sessions`)。名前の中の `_` は 2 つ重ねるので、同じ名前の静的な段 (`/blog/id` と `/blog/[id]`、`/` と `/root`) が同居しても別の id になる
- 列挙が「id が 2 つのファイルから出た」で失敗したら、記号だけが違う名前の画面が同居している (例: `/a.b` と `/ab`)。黙って片方を捨てず、`id.replace` にそのリポジトリ向けの置換を足して区別する
- `_folder` (名前が `_` で始まるディレクトリ) の下はルーティングの対象外なので、そこの page ファイルは入口にしない (既定の `exclude`)
- layout ファイルは、抽出器 `next-layouts` が画面とは別の入口として拾う。階層パスは `/(layout)` で始まり、後ろに枠の置き場のフォルダが続く (例: `src/app/(main)/layout.tsx` → `/(layout)/(main)`、app 直下の layout → `/(layout)`)。どの入れ物の枠かが名前になるので、`(group)` は落とさない。id は `layout_l` で始まり、入れ物は `_g` の印で表す (例: `layout_l.main_g.websites.websiteId_d`)
- どの画面がどの枠を通るかは、列挙ツールがソースのフォルダの親子から決めて、入口の一覧の `within` (包む入口の id、外側から) に書く。エージェントは決めない・書き換えない
- `template`、`loading`、`error`、`not-found`、`default` (並行ルートの既定の中身) のファイルは、既定の抽出器では拾わない。画面も枠もこれらを辿らないので、**入口を発見するときに、これらのファイルの有無と中身を確かめる** (数は少ない)
  - データの読み書きにも外部への送信にも至らない (固定の文言や `null` を返すだけ) → 入口にしない。確かめたことを抽出器の `rationale` に書く
  - データの読み書きや外部への送信に至る部品を描く → そのリポジトリの入口の一覧に、そのファイルを拾う抽出器を**必ず足す** (`abatlas-extract glob`、`layer: page`、`segments.prefix` で階層を分ける。例: `(default)`)。足さないと、その処理はどの入口の結果にも現れない
- 保存された設定で、描く部品が決まる画面 (名前から部品を引く登録表を持つ作り) があるときは、部品を別の入口に分けるかを決める (下の「登録表から選ばれて描かれる部品」)
- `route.ts` (API の受け口) は入口にしない。画面から辿った途中のフレームとして現れる。画面を通らない受け口 (外部向け API、計測の受信) は、このプロファイルの既定では分析の対象にならない
- `middleware.ts` (Next.js 16 からは `proxy.ts`) は、下の「middleware」の節で決める

### middleware

`middleware.ts` は、リクエストごとに、画面より先に動く (ログインの確認と転送、独自ドメインの振り分けなど)。App Router でも Pages Router でも同じ扱いにする。

- **入口を発見するときに、中身を確かめる**。データの読み書きか外部への送信に至る (トークンの検証で DB を読む、計測を外へ送る、など) ときだけ、抽出器 `next-middleware` を入口の一覧に書く。転送や書き換えだけなら書かない (確かめたことを報告に書く)
- 階層は `/(layout)/_middleware`、id は `layout_l.middleware_a`。層は `layout` (画面を包む共通の枠と同じ扱い)
- 置き場がリポジトリの直下 (か `src`) なので、列挙ツールは、これが**すべての入口を包む**と決める。`config.matcher` で動く URL を絞っていても、包む関係は絞らない。どの URL で動くかは、入口の `summary` に書く
- 画面と枠は middleware を辿らない (入口の一覧に入れていなくても、辿らない)。middleware を分析するときは、`middleware` の関数から呼ぶ関数を、枠と同じ基準で終端まで辿る。URL や host で分かれる処理は、それぞれを `conditional` にして、条件を `summary` に書く

## Pages Router の画面

`pages/` の下のファイル 1 つ = 画面 1 つ。App Router と違う所だけを書く。

### 入口の判別

| もの | 入口 | 抽出器 |
|---|---|---|
| `pages/**/*.tsx` など (下の 5 つと `api/` を除く) | 画面 (`page`) | `next-pages-router` (index 以外)、`next-pages-router-index` (index) |
| `pages/_app.tsx` | すべての画面を包む枠 (`layout`)。階層 `/(layout)/_app`、id `layout_l.app_a` | `next-pages-app` |
| `pages/_document.tsx` | 既定では入口にしない。HTML の骨組みで、ふつうはデータを読まない。中身を確かめ、`getInitialProps` などでデータに届くときだけ、`next-pages-app` と同じ形の抽出器を足す (階層 `/(layout)/_document`) | — |
| `pages/_error.tsx`、`pages/404.tsx`、`pages/500.tsx` | 既定では入口にしない。App Router の `error` と `not-found` と同じく、中身を確かめ、データに届くときだけ足す (`layer: page`、`segments.prefix` で階層を分ける。例: `(error)`) | — |
| `pages/api/**` | 入口にしない。画面から辿った途中のフレーム (`api_route`) として現れる。画面から呼ばれない受け口 (webhook、定期の処理の受け口、外部向けの API) は、App Router の `route.ts` と同じく、このプロファイルの既定では分析の対象にならない | — |

- 階層パスは URL の形。拡張子を除いたファイル名が最後の段で、ファイル名の `index` は段にしない (`pages/index.tsx` → `/(root)`、`pages/documents/index.tsx` → `/documents`)。`index` という名前の**フォルダ**は段に残す (だから、index とそれ以外で抽出器を分けている)
- 段の印は App Router と同じ (`[id]` → `id_d`、`[...name]` → `name_c`、`[[...slug]]` → `slug_o`、直下の index → `root_r`)。同じ URL は、App Router でも Pages Router でも同じ id になる (移行しても、入口の id が変わらない)
- `app/` と `pages/` の両方があるときは、両方の抽出器を書く。Next.js は同じ URL の画面を両方に置くとビルドで止めるので、ふつう id はぶつからない。列挙が「同じ id」で止まったら、どちらかが古いファイルで残っている。黙って片方を捨てず、報告する
- 包む関係 (`within`) は列挙ツールが決める。`_app` は `pages/` の下の画面だけを包み、App Router の画面は包まない (実際の動きと同じ)。App Router の layout も、Pages Router の画面を包まない
- 抽出器の属性: `server_props` (`getServerSideProps` がある)、`static_props` (`getStaticProps` がある)、`initial_props` (`getInitialProps` がある)。分析の手がかりにする

### 多くの page が自分で描く共通の枠

Pages Router には、フォルダごとの layout ファイルが無い。共通の枠 (メニュー、ヘッダー、ログインの確認、所属の読み込み) は、**page が自分で描く** (`<AppLayout>` で中身を包む。または `Page.getLayout` で枠を返し、`_app` が `Component.getLayout` を呼んで包む)。画面ごとに辿ると、同じ経路を画面の数だけ繰り返す (App Router の layout と同じ問題)。

- **入口を発見するときに**: 中身 (`children`) を包む枠のコンポーネントのうち、**3 つ以上**の page が描き、データの読み書きか外部への送信に至るものを、入口に足す。`abatlas-extract listed` (名前は `agent-listed-layout`、`layer: layout`)
  - 階層パスは `/(layout)/_shared/<コンポーネントの名前>`、id は `layout_l.shared_a.<コンポーネントの名前>` (名前の中の `_` を 2 つ重ね、それ以外の記号を除く)。名前は export している名前 (無名なら、拡張子を除いたファイル名)
  - `source` はコンポーネントの定義の行。`reason` に、描く page の数と、例の page を 2〜3 書く
  - 列挙の後、その入口が何も包んでいない (`within` で、ほかの入口から指されていない) ことを確かめる。包む関係は置き場のフォルダで決まるので、枠のファイルと同じフォルダに入口のソースがあると、包むと判定される。そのときは報告する
- **画面を分析するとき** (枠が入口の一覧に入っているとき。承認の前の `candidate` でも同じ): 枠のコンポーネントは辿らない。page の入口のフレームの `links` に `kind: embed`、`target` は枠のコンポーネントの名前、`entry_id` は枠の入口の id、`status: fact` (根拠は、page が枠を描く行) を書く。`getLayout` のときは、`getLayout` の中で枠を描く行を根拠にする。枠の入口を後で外したら、その枠を描く page を分析し直す (入口を発見する側が、報告に書く)
- **枠を分析するとき**: App Router の layout と同じ。`children` (や `getLayout` に渡される page) の中身は辿らない
- 入口の一覧に入っていない枠 (描く page が 2 つ以下、データに届かない) は、これまでどおり、画面の中で辿る
- `_app` が URL で包み方を変える (例: ある URL の一覧に入る画面だけ、所属の読み込みをしない) ときは、`_app` の入口の `summary` に条件を書く (App Router の「枠の動きが画面や URL によって変わるとき」と同じ)。`router.pathname` は動的な段を `[id]` の形のまま持つので、一覧の URL と完全に一致する page ファイルを `pages/` の下で確かめ、当たる page を `summary` に書く (一覧にあっても、当たる page が無い URL や、App Router の画面の URL がある)。包み方で動きが変わる部品は `conditional` にする

### `_app` を分析するとき

- `_app` は、props の `Component` (開いた page) を、Provider (値を配る部品) で包んで描く。`Component` の中身は辿らない (App Router の layout の `children` と同じ)
- フレームにする Provider は、データの読み書きか外部への送信に至るもの (所属のチームを読む、計測を送る)。見た目だけの Provider (テーマ、ツールチップ、通知の枠) は `summary` で名前に触れるだけ
- Provider の JSX の中に書いた子の部品の `caller` は、その JSX を書いた部品 (ふつうは `_app` の入口のフレーム)。`children` を通すだけの Provider は、呼び出し元にしない
- **画面を分析するとき**: `_app` の Provider が配る値を読むだけのフック (`useContext` を返すだけ。例: 所属のチームを返すフック) は、段にしない。その値を作る読み書きは、`_app` の入口に書く
- ライブラリの Provider が、自分のシステムの受け口を呼ぶ (例: `next-auth` の `SessionProvider` が `/api/auth/session` を呼ぶ): セッションがデータベースに無い (JWT) ときは、ライブラリの呼び出しを `external` の 1 段にして閉じ、受け口のファイルは辿らない。データベースにあるときは、受け口をフレームにして I/O を書く
- Pages Router の画面、`_app`、`pages/api` の受け口で、セッションの確認がデータを読まない (JWT の検証だけ。例: `getServerSession`、`getToken`) ときは、段にせず、確かめる側の段の `guards` (authentication) にだけ書く。ログインしていないと呼ばない取得 (`session ? url : null`) は `always` にし、`guards` に書く

### 画面の分析: サーバー側でデータを読む関数

page のファイルが export する `getServerSideProps`、`getStaticProps`、`getInitialProps` は、Next.js が描画の前に呼ぶ、サーバー側の関数。

- それぞれを `api_route` のフレームにする (page と別の層にする。突き合わせは「層とファイル」で照合するので、同じ層だと page のフレームと 1 つに潰れる)。`name` は関数の名前、`source` は定義の行、`caller` は page の入口のフレーム。`call` の根拠は定義の行 (Next.js が名前で呼ぶので、呼び出しの行は無い)、`status: fact`
- そこから先は、App Router の `api_route` と同じ (入力の解釈、認証・権限の検査、呼ぶサーバー側の関数 → `query` → `external`)
- `getStaticProps` は、作るとき (と `revalidate` の間隔) に動く。開くたびではないことを、フレームの `summary` に書く。`getInitialProps` はクライアント側の遷移ではブラウザで動くことも、`summary` に書く
- `getStaticPaths` は、データを読むときだけフレームにする (`paths: []` を返すだけなら、page の `summary` に触れるだけ)
- 同じファイルの page のコンポーネントは、受け取った props で描くだけなので、データ取得の関数を「呼ぶ」側ではない。木は page の入口のフレーム → データ取得の関数 (`api_route`) と、page の入口のフレーム → 描くコンポーネント (`component`) の 2 本に分かれる。辿る順は、ファイルの行の順 (データ取得の関数が page の本体より前に書いてあれば、そちらが先)
- 翻訳の読み込みだけをする補助の関数 (翻訳のファイルを集めて props にする) は、段にしない (「翻訳・日付・書式の小道具」と同じ)

### 画面の分析: `pages/api` の受け口

- URL から受け口を探す手順 (下の「component から api_route への橋渡し」の 3) で、`pages/api/<URL の残り>.ts` と `pages/api/<URL の残り>/index.ts` も探す (`${…}` の部分が `[id]` の段に当たる)。app と pages の両方にあるリポジトリでは、両方を探す
- 受け口は default export の関数 1 つで、`req.method` で分かれる。フレームは、App Router の route ファイルと同じく、**HTTP メソッドごと**に分ける (`name` は `GET /api/…`)。`source` は、そのメソッドの分岐の行 (`if (req.method === "GET")`、`switch` の `case "GET":`)。分岐が無く、どのメソッドでも同じ処理なら、関数の定義の行にして、`name` は `ALL /api/…`
  - 先頭で 1 つのメソッド以外を断るだけ (`if (req.method !== "POST") return …`): `name` はそのメソッド、`source` はその行
  - 別のファイルの関数を出し直すだけの受け口 (`export { default } from "…"`): 出し直し先の関数で、上と同じに決める (`source` は出し直し先のファイル)
  - ライブラリが中でメソッドを振り分ける受け口 (ファイルの受け取りのライブラリなど): `ALL` の 1 段
- 受け口を包む関数 (認証を確かめてから中の関数を呼ぶ、共通の包み。例: `withTeamApi(handler, { role })`) は、その受け口の経路として、`query` の段にする (`api` プロファイルの「操作に掛かる middleware」と同じ)。受け口ごとに違う、求める権限は、受け口の段の `guards` に書く
- `next-auth` の `[...nextauth].ts` などの、ライブラリが受け持つ受け口は、ライブラリの呼び出し (`NextAuth(authOptions)`) を `external` にして閉じ、`authOptions` の中のコールバックが読み書きするものは、そのフレームの I/O に書く

## 入口ごとの分析で見るもの

| 層 | 読む場所 | 拾うこと |
|---|---|---|
| page | page ファイル | 描画するコンポーネント、URL のパラメータ (`params`)。祖先ディレクトリの `layout` ファイルは読まない (別の入口) |
| layout | layout ファイル | 枠が描画するコンポーネント (ヘッダー、メニュー、ログイン確認、条件付きで開く小窓)、URL のパラメータ。`children` と並行ルートの props の中身は読まない (包まれる側の入口) |
| component | コンポーネントとフックのファイル | 子のコンポーネント、呼ぶフック、フックが呼ぶ API の URL と HTTP メソッド、書き込み (作成・更新・削除) を起こす操作 |
| api_route | URL に当たる `route` ファイルの、HTTP メソッドの名前の関数。または `'use server'` の関数の定義 | 入力の解釈、認証・権限の検査、呼ぶサーバー側の関数 |
| query | サーバー側の関数のファイル | テーブルと操作 (ORM のメソッド、SQL)、キャッシュのキー、メッセージの送り先、外部 API の host / path |

### フレームにするもの・しないもの

フレームが際限なく増えないように、次の基準で選ぶ。

- **フレームにする**: データを読む・書く処理に至る経路の上にあるコンポーネントとフック。API を呼ぶフックは 1 つずつフレームにする
- **フレームにしない**: 見た目だけの部品 (ボタン、表の枠、アイコン、UI ライブラリの部品)、翻訳・日付・書式の小道具、型定義。経路の上に無いものは `summary` で触れるだけでよい
- **画面と、画面を包む枠 (layout)**: 画面を開くと、祖先ディレクトリの `layout` ファイルと、そこから描かれる共通の部品 (ログイン確認、設定やユーザーの読み込み、共通のヘッダーやメニュー、条件付きで開く小窓など) も動く。これは画面ごとに書かず、**枠を 1 件の入口として 1 回だけ分析する**。同じ枠を通る画面が何十もあり、画面ごとに書くと同じ経路を画面の数だけ繰り返すため。どの画面がどの枠を通るかは、入口の一覧の `within` が持つ
  - **画面 (`page`) を分析するとき**: 祖先ディレクトリの layout と、そこから描かれる部品は**辿らない**。フレームにも I/O にも書かない。書くのは、page ファイルから描画する側だけ。入口の `summary` にも枠の処理を書かない (どの枠を通るかは画面が一覧から出す)
  - **枠 (`layout`) を分析するとき**: 入口のフレームは layout ファイル (`layer: layout`)。layout が描画するコンポーネントを、画面と同じ基準で終端まで辿る。`children` と、並行ルートの props (`@modal` に当たる `modal` など) の**中身は辿らない** (包まれる側の入口で分析する)。外側・内側の別の layout も辿らない (それぞれ別の入口)
  - 枠の中で条件付きで動くもの (ある設定が有効なときだけ、ある状態のときだけ開く小窓) も辿る。条件は、そのフレームの `summary` か I/O の `note` に書く。枠の動きが画面や URL によって変わるとき (例: 特定の画面ではメニューを出さない、データが無ければ何も描かない) は、その条件を入口の `summary` に書く
  - 枠が描く部品と同じ部品を、画面も自分で描いているとき (例: 同じフックを page 側のコンポーネントも呼ぶ) は、画面の側にも書く。省くのは「枠を経由してだけ動くもの」
  - データの読み書きにも外部への送信にも至らない枠 (翻訳や見た目の設定だけ) は、「データに届かない画面」と同じ書き方で閉じる
- **`external` フレームの場所 (`source`)**: ライブラリのソースはリポジトリに無いので、`source` には**ライブラリの関数・メソッドを実際に呼んでいる行**を書く (例: `prisma.client.user.findUnique(…)` の行、`client.get(key)` の行)。クライアントを作る・設定するだけの共通ファイルの行や、import の行を `source` にしない。リポジトリが自前の関数でライブラリを包んでいて、ライブラリのメソッドを呼ぶ行がその関数の中にあるとき (例: `lib/redis.ts` の `get` の中の `client.get`) は、その行が `source` になる
- **終端の決まり**: 機械チェックは、終端のフレーム (誰からも呼ばれないフレーム) が「`external` の層」「I/O を持つ」「業務のルールを持つ」「行き先の入口が分かっているつながり (`links` の `embed` / `trigger` と `entry_id`) を持つ」「権限の確認を持つ」「`unknown` の主張を持つ」のどれかであることを求める。だから、経路は必ずデータの I/O か `external` のライブラリまで書き切る。途中で止めたフレームを終端にしない
- **データに届かない画面・枠** (別の画面へ転送するだけ、固定の文言を出すだけ、翻訳や見た目の設定だけ): 入口のフレームから、それが最後に頼るライブラリ (転送なら `next/navigation` のルーター、翻訳なら翻訳のライブラリ) を `external` フレームとして 1 つ書いて閉じる。I/O は無し。「データを読まない」ことは入口の `summary` に書く
- **同じファイルに複数の関数**: フレームはファイル単位を基本にする。`route` ファイルだけは HTTP メソッドごとにフレームを分ける (`name` に `GET /api/…` のように書く。呼び出し元のフックがメソッドごとに違うため)。`'use server'` のファイルに関数が複数あるときも、呼ばれる関数ごとに分ける
  - 正解との突き合わせ (`abatlas evaluate`) は、フレームを「層と `source.file`」で照合するので、同じ `route` ファイルの GET と POST は 1 つに数えられる。メソッドの取り違えは、フレームではなく I/O の照合 (種類・操作・段) に現れる。フレームを分けるのは、画面と図で呼び出しの関係を正しく見せるため

### 登録表から選ばれて描かれる部品 (`part`)

画面が、**保存された設定** (データベースに保存した画面の構成、利用者が選んだ部品の種類) で、描く部品を決める作りがある。コードには、名前から部品を引く**登録表** (例: `registry[type]`、種類の名前 → コンポーネントの対応表) があり、どの部品が描かれるかは、実行時の値で決まる。候補をすべて 1 つの画面の中で辿ると、1 件の分析がとても大きくなり (実物で、フレームが 300 を超えた)、同じ部品を、登録表を使う画面の数だけ繰り返すことになる。

そこで、**部品を、部品ごとに別の入口に分けられる**。分けるかどうかは、入口の一覧で決まる。

| 入口の一覧 | 画面の分析 |
|---|---|
| その登録表の部品が、`part` の入口として入っている | 画面は、登録表を引くフレームで止める。部品は、部品の入口で分析する |
| 入っていない | これまでどおり、候補が有限で全部読めるなら、画面の中で、それぞれをフレームにする |

**入口を発見するとき**:

- 登録表を見つける (種類の名前からコンポーネントを引く対応表のうち、**保存された値** (データベースに保存した構成、保存の前に利用者が選んでいる最中の値) で引くもの)。URL の段や、画面の中の切り替え (タブ) で引く対応表は、登録表に当たらない (経路の表なので、これまでどおり、画面の中で辿る。ただし、下の「既にある入口と同じ部品」は当てはまる)。候補のうち、データを読む・外へ送る部品が **3 つ以上**あれば、部品を入口に分ける。2 つ以下なら分けない (画面の中で辿る)。迷うときは分け、迷ったことを `reason` に書く (承認のときに、人が外せる)
- 登録表の項目 1 つ = 入口 1 件。`abatlas-extract listed` で足す (抽出器の名前は `agent-listed-part`、`layer: part`)
  - 階層パスは `/(part)/<登録表の名前>/<選ぶときの名前>`、id は `part_p.<登録表の名前>.<選ぶときの名前>` (id では、画面の id と同じく、名前の中の `_` を 2 つ重ね、それ以外の記号を除く。例: 登録表 `boardComponentRegistry` の `WebsiteChart` → `/(part)/boardComponentRegistry/WebsiteChart`、`part_p.boardComponentRegistry.WebsiteChart`)
  - 「登録表の名前」は、登録表を定義しているファイルの名前から、拡張子を除いたもの (中の変数の名前ではない)。1 つのファイルに登録表が 2 つ以上あるときだけ、変数の名前を使う
  - 「選ぶときの名前」は、登録表のキー (保存された設定に入る値)。コンポーネントの名前と違うときも、キーを使う。キーが空の文字の項目は、同じ部品を指す別のキーがあれば足さず、無ければ `(empty)` という名前にする
  - `source` は、登録表の、その項目の始まりの行 (項目が複数行なら、最初の行)。`reason` に、どの登録表の項目か、どの画面が、登録表から部品を引いて描くか (ファイルと行) を書く
- データを読まず、外へも送らない部品 (文字を出すだけなど) は、入口にしない。確かめたことを、抽出器の `rationale` に書く
- 登録表の項目が、条件で別のコンポーネントに替わるとき (対象の種類ごとの部品を持つ) も、入口は項目ごとに 1 件 (替わる先は、部品の入口の中で辿る。下の「部品を分析するとき」)
- **既にある入口と同じ部品**: 対応表の項目が指すコンポーネントが、既にある画面の入口の本体と同じ (その画面の page ファイルが、そのまま描くコンポーネント) なら、新しい `part` を作らない。描く側の画面は、その画面の入口を `embed` で指す (同じ分析を 2 回しない)。これは、登録表に当たらない対応表 (URL の段で引くもの) にも当てはめる
- 部品の入口を足した・外したときは、登録表から部品を引いて**描く**画面の結果が古くなる (登録表を、有無の確認や一覧の表示に使うだけの画面は、含めない)。報告に、分析し直す画面を書く
- どの画面が部品を描くかは、入口の一覧には書かない。画面の結果のつながり (`embed`) から、集計 (入口どうしのつながりの表) が出す。部品の入口に付く `within` は、列挙ツールが、登録表のファイルの置き場から決めたもの (その置き場を包む枠) で、描く画面を表すものではない

**画面 (や枠) を分析するとき** (登録表の部品が、入口の一覧に入っているとき):

- 登録表を引くフレーム (登録表から部品を引いて描く component) までを書き、**その先の部品は辿らない**
- そのフレームの `links` に、入口になっている部品を 1 件ずつ書く: `kind: embed`、`target` は選ぶときの名前 (登録表のキー)、`entry_id` は部品の入口の id (既にある画面の入口と同じ部品なら、その画面の入口の id)。`embed` では、`entry_id` を必ず書く (機械チェックが見る)。部品は実行時の値で選ばれるので、`status` は `interpretation` (根拠は、登録表を引く行と、登録表の項目の行)
- どの値で部品が選ばれるか (保存された設定のどの項目か) を、そのフレームの `summary` に書く
- 入口にしなかった部品 (データを読まないもの) は、`summary` に名前を書くだけでよい
- 保存の前に、選んでいる最中の値で部品を描く所 (部品を選ぶ画面の試し描き) も、同じ登録表から引くので、同じように止めて `embed` を書く
- 既に結果がある画面を、部品を分けた後に分析し直すとき: 残したフレームの文 (`summary`、`note`) に、外した部品の中の話が残っていないかを確かめる。部品を外すと、「同じ処理は、最初に着いた呼び出し元の下に書く」の置き場が動くことがあるので、もう一度書いたフレームの置き場も確かめ直す
- 既にある画面の入口を `embed` で指すとき、描く側で前提が違うこと (権限の確認が別、対象の決まり方が別) があれば、そのフレームの `summary` に書く
- 登録表を引くフレームは、読み書きを持たなくても終端にできる (`embed` のつながりがあるため)
- 同じ登録表を引くフレームに、2 つの経路で着くとき (列の表示と、部品を選ぶ画面の試し描き): `embed` は、最初に着いたフレームに書き、ほかの呼び出し元は、`summary` に「経路はフレーム `<id>` と同じ」と書く
- `embed` の `target`: 選ぶ表のキーが無いとき (条件の分かれ道で描く) は、コードの値のとおりに書く。別のキーが、同じ入口を指すときは、1 件にまとめる
- `links` に書かないもの: URL のクエリだけを書き換える操作 (同じ画面の絞り込み)、外のサイトを開くリンク。`summary` に書く

**部品 (`part`) を分析するとき**:

- 入口のフレームは、登録表の項目が指すコンポーネント (`layer: part`)。入口のフレームの `source` は、コンポーネントの定義の行 (結果の `entry.source` は、入口の一覧のまま、登録表の項目の行)。そこから、画面と同じ基準で終端まで辿る
- 部品を描く側 (画面、登録表を引くコンポーネント、枠) は辿らない。描く側から受け取る値 (対象の id、部品の設定) は、入口のフレームの `parameters` に書く。props のほかに、描く画面の URL のクエリから読む値 (期間、絞り込みなど) と、アプリの状態から読む値 (タイムゾーンなど) も、同じく `parameters` に書く
- 登録表を引くフレーム (描く側) が、部品を描く前に確かめている条件 (例: 対象の id が無ければ描かない) は、部品の入口の前提として使ってよい (`parameters` の `note` に、描く側の行と一緒に書く)。それより外の画面の事情 (どの画面も、その値を渡さない) は、理由にしない
- 保存されたデータや URL から来る値を、固定の一覧で絞っている所は、固定の値で閉じた扱いにしない (`conditional` で辿る)
- 登録表の項目が、条件で別のコンポーネントに替わるとき (項目が、対象の種類ごとの部品を持ち、描く側が選ぶ): 替わる先のコンポーネントを、入口のフレームの下に `conditional` で足して辿る (`call` の根拠は、登録表の項目の行と、描く側が選んでいる行)。どれを選ぶかの判定は、描く側 (登録表を引くフレーム) の `rules` に書く
- 描く側が渡す値で動きが変わるとき (ある設定を渡したときだけ読む) は、候補をすべて辿り、`conditional` にして条件を書く。フックが、渡された値で API の呼び出しを止める作り (`enabled: ...`) では、フックの呼び出しは `always`、フックが API を呼ぶ段を `conditional` にする。呼び先は変わらず、送る値だけが変わるときは、フレームを分けず、その値を使う段の `rules` に書く。「どの画面も、その値を渡さない」ことは、部品の入口からは決められないので、理由にしない (分析の skill の「固定の値で閉じている呼び出し」に当たるのは、部品の木の中のコードが、子に固定の値を直接書いて渡しているときだけ。そのときは、その先を辿らない)
- 権限の確認、設定、業務のルールは、部品の経路の上にあるものを、部品の結果に書く (描く側の結果には書かない)

### 同じ処理が何度も呼ばれるとき

1 つの入口の中で、同じ処理が複数の呼び出し元から呼ばれることがある (例: どの API の受け口も、最初にログイン確認を呼ぶ)。ここでの「同じ処理」は、**同じ関数** (定義の行が同じ関数・コンポーネント・フック・`route` のメソッド。`external` フレームなら、ライブラリを呼んでいる同じ行) のこと。同じファイルにある別の関数 (例: 同じ query ファイルの、読む関数と更新する関数) は同じ処理ではないので、まとめずにそれぞれ書く。フレームは木 (`caller` は 1 つ) なので、次のように書く。

- その処理と、そこから先の経路 (呼び先のフレームと I/O) は、**呼び出し元 1 つの下に 1 回だけ**書く。どの呼び出し元の下に書くかは、**入口から辿る順**で決める: 入口のフレームから、呼び出しを、コードに書いてある順 (同じ関数の中では行の順、同じ行なら左から) に、深さ優先で辿り、最初にその処理に着いた呼び出し元の下に書く (実際に動く順に近い木になり、分析者が違っても同じ木になる)
- それ以外の呼び出し元では、フレームを足さない。呼び出し元のフレームの `summary` に「<処理の名前> も呼ぶ。経路はフレーム `<id>` と同じ」と書く
- フレームを足さないと呼び出し元が終端になり、終端の決まりを満たせないとき (その呼び出し元の呼び先が、すべて他の呼び出し元の下に書いた処理のとき) だけ、呼び先のうち、コードに書いてある順でいちばん早い呼び出しの 1 つを、その呼び出し元の下に、もう一度書く。書くのは、終端の決まりを満たす最初のフレーム (読み書きを持つフレームか、`external` のフレーム) まででよい。もう一度書いたフレームには、権限の確認・設定・業務のルールを繰り返さない (最初に書いたフレームだけに書く)
- 同じ関数でも、呼び出し元によって違うテーブルや URL に届くもの (引数で読み書き先が変わる) は、同じ処理として省かない。届く先ごとに書く

何度も書くと、読み書きの件数が呼び出しの回数だけ水増しされ、分析の費用も増える。1 回だけ書けば、「この画面がどのデータに触れるか」は変わらずに残る。

### component から api_route への橋渡し (このプロファイルの要)

ブラウザ側からサーバー側へ入る口は 2 種類あり、辿り方が違う。まずどちらかを見分ける。

| 入り方 | 見分け方 | 辿り方 |
|---|---|---|
| URL で呼ぶ (Route Handler) | フックや `fetch` に URL の文字列がある | 下の 1〜5 の手順で `route` ファイルに対応付ける |
| 関数を呼ぶ (Server Function) | 呼んでいる関数の定義が、先頭に `'use server'` のあるファイル (または関数の先頭に `'use server'`) にある。フォームの `action` に渡す関数もこれ | 関数の**定義**まで辿り、その関数を `api_route` フレームにする。import されていれば import を辿る。props で受け取った関数なら、渡している親のコンポーネント (page まで) を逆に辿って定義を見つける。`call` の evidence は呼び出し (または `action=` に渡している) 行。URL も `route` ファイルも探さない |

Server Function が page やコンポーネントのファイルの中に定義されている (関数の先頭に `'use server'`) ときは、定義のあるファイルが `page` / `component` のフレームと同じになる。そのときも `api_route` フレームを別に作り (`source` は関数の定義の行、`caller` は実際に呼ぶ・`action` に渡すコンポーネント)、定義を props で渡しているだけのファイルは経路として `summary` に書く。渡し元を辿り切れないときは、呼び出し側のフレームに `unknown` + `dynamic_dispatch` を書く。

URL で呼ぶ場合、関数の呼び出しを追うだけでは辿れないので、次の手順で対応付ける。

1. フックや `fetch` の呼び出しから、URL の形と HTTP メソッドを読む (例: ``get(`/websites/${websiteId}/stats`)`` → `GET /websites/<動的>/stats`)
2. 共通の接頭辞を確かめる (API クライアントが `/api` を前に付けることが多い。付ける場所を 1 度読んで evidence にする)
3. app ディレクトリの下で、その形に当たる `route` ファイルを探す (`${…}` の部分が `[id]` の段に当たる。例: `app/api/websites/[websiteId]/stats/route.ts`)。pages ディレクトリがあれば、`pages/api` の下も探す (「Pages Router の画面」の節)
4. その `route` ファイルの、HTTP メソッドと同じ名前の関数 (`export async function GET`) を `api_route` フレームにし、`caller` で呼び出し側のフックを指す
5. `call` の evidence は **呼び出し側の URL の行** (フックのファイル)。受け口の関数の行はフレームの `source` に書く

状態の付け方:

- URL の形が文字列としてそのまま読め、当たる `route` ファイルが 1 つに決まる → `fact`
- URL が変数や引数で組み立てられ、候補が複数ある → 候補が有限で全部読めるなら、それぞれフレームにして `interpretation` (`note` に「引数で切り替わる」)。決められないなら `unknown` + `dynamic_dispatch`
- 当たる `route` ファイルが scope に無い (別のサービスの API) → フレームにせず、呼び出し側の `io` に `external_api` として書く

## 事実・解釈・不明の付け方

- **fact**: コードにそのまま書いてある (import と呼び出し、URL の文字列、ORM のメソッドとモデル、SQL の `from website_event`)。根拠はその行
- **interpretation**: 読み取って要約したもの (フレームの summary、何のための処理か)。根拠は読んだ範囲の代表行
- **unknown**: 次の典型例ではこの理由を使う
  - URL やテーブル名が実行時の値で決まり、静的に読めない → `dynamic_dispatch`
  - 設定や DB に保存された定義から問い合わせを組み立てる → `generated_at_runtime`
  - 呼び先が scope の外、または別のパッケージ → `out_of_scope`
  - 配布物だけでソースが無い → `binary_or_vendored`

### 接続先 (host / database) の扱い

DB やキャッシュの接続先は、実行環境の設定 (`DATABASE_URL` などの環境変数) で決まり、どの画面でも同じになる。このプロファイルでは次のように書く。

- 接続先の段 (`host`、`database`、`instance`、`broker`) は**書かない**。値をリポジトリから読めないため
- テーブル・キー・トピックの名前がコードから読めれば、その I/O は `fact` にする (接続先が環境変数であることだけを理由に `unknown` にしない)
- 接続先がコードに直接書いてあるとき (固定の外部サービスなど) は、その段を書く

## データの当てはめ

- ORM のモデル → `rdb`。テーブル名はモデルの定義で確かめる (Prisma なら `schema.prisma` の `@@map`。無ければモデル名)。段は `dbms` と `table` (分かれば `schema`)
  - Prisma のメソッド: `findMany` / `findUnique` / `findFirst` / `count` / `aggregate` / `groupBy` → `read`、`create` / `createMany` → `create`、`update` / `updateMany` → `update`、`upsert` → `create` と `update` の 2 件、`delete` / `deleteMany` → `delete`
  - 生の SQL: `select … from` と `join` の表 → `read`、`insert into` → `create`、`update` → `update`、`delete from` → `delete`
- **同じ処理に複数の DB 向けの実装があるとき** (設定でどちらか一方が動く。例: PostgreSQL 用と ClickHouse 用の SQL を並べて持つ) は、**両方**を I/O に書く。`dbms` の段で分ける (`postgresql` / `clickhouse`)。どちらもコードにあるので `fact`。フレームの `summary` に「設定でどちらかが動く」と書く
- Redis などのキャッシュ → `kvs` (`namespace` / `key_pattern`。キーが組み立て式なら変数の部分を `*` にする。操作は get / set / delete / expire)
- Kafka などのメッセージ基盤 → `queue` (`topic`。操作は publish / consume)
- サーバーから他社のサービスを呼ぶ HTTP → `external_api` (`op: call`、host / path)
- ブラウザの中の保存 (localStorage、sessionStorage、cookie の読み書き) は、サーバーのデータではないので **I/O に書かない**。画面の動きに効くなら、そのフレームの `summary` に書く
