# ui-vue-router プロファイル: エージェント向けの説明

対象は「Vue Router で作った、画面を持つシステム」。画面の定義 (ルーティング) をコードの中に書き、バックエンドの API は、別のリポジトリか、分析の範囲の外にあるもの。入口の発見と入口ごとの分析で、このファイルと `profile.yaml` の両方を読む。

## アーキテクチャと層の連鎖

```text
screen (route 1 つ = 画面 1 つ)
  → component (Vue コンポーネントと composable)
    → store (Pinia / Vuex。状態と、API を呼ぶ action)
      → api_client (HTTP を包む自前の関数。無いシステムもある)
        → external (HTTP のライブラリ、生成された SDK。ここで終端)
              ⇢ バックエンドの API (範囲の外。I/O の external_api として書く)
```

- `screen` と `shell` が `role: entry`。route 1 つ = 入口 1 件。アプリ全体の枠 = 入口 1 件 (`shell`)
- `shell` は、連鎖の先頭が `shell` に替わるだけで、その先は同じ。画面と枠は**別々に分析する** (下の「画面と、アプリ全体の枠」)
- `external` が `role: boundary`。ライブラリや SDK の呼び出しに達したら、コールスタックを閉じる
- 層は飛ばしてよい。コンポーネントが store を通さずに SDK を直接呼ぶなら、`component → external` とつなぐ。層を行き来してもよい (例: store → 補助の関数 → store)
- 層の当てはめに迷う関数 (`utils/` などの、コンポーネントでも store でもない関数) は、次で決める: HTTP や外部のライブラリを包む関数 → `api_client`。それ以外 (store を呼ぶだけの補助の関数など) → `component`
- フレームの `kind` は、次の語から選ぶ: `route` (入口の画面)、`shell` (入口の枠)、`component`、`composable`、`function`、`store_action`、`sdk`、`library`
- バックエンドの API は、フレームにしない。呼び出す行のフレームの `io` に、`external_api` として書く (下の「データの当てはめ」)

## 入口の判別 (抽出器のパラメータの決め方)

入口を列挙する主体は、エージェントである。抽出器 `vue-routes` は、文字で書いた定義だけを取る。**取れない定義が、ふつうにある**。

1. 画面の定義の場所を見つける。`createRouter` に渡している `routes` を辿る (`routes.ts`、`router/index.ts` など)。`files` をそのファイルに合わせる
2. 列挙を試す。出力の「読めなかった参照」を、1 件ずつ読む
3. 読めなかった定義から、入口を足す (`abatlas-extract listed`)

| 読めなかった参照の形 | 読む場所 | どう足すか |
|---|---|---|
| 別のファイルで定義して、名前で並べた route (`FLOW_ROUTE`) | その名前の定義 (import を辿る) | 定義の `path` から入口を足す。`source` は定義の行 |
| `name` を定数や、組み立てた文字で書いた route | 定数の定義 | `path` が文字で読めれば足す。`source` は、route のオブジェクトの始まりの行 (列挙が知らせるのは `name:` の行なので、ずれることがある)。`name` は定数の値 |
| 展開した配列 (`...otherRoutes`) | 展開している配列の定義 | 配列の中の route を、1 つずつ足す |
| 関数が作る route (`makeRoutes()`) | 関数の定義と、渡している引数 | 作られる route の数と `path` が、コードの固定の値から決まるなら足す。実行時の値 (設定、サーバーの応答) で決まるなら足さず、報告に場所と理由を書く |
| 入れ子の route (`children`) | — | 入口にしない。親の画面に含める (下の「入れ子の route」) |
| `redirect` の中の `name` など、route の定義でないもの | — | 入口にしない |

- 階層パスは、URL の形。実行時に値が入る段 (`:id`) は残す。ほとんどの画面の先頭に付く、共通の段 (例: 省ける先頭の `:tenant?`) は、`segments.drop` で落とす (`drop` は正規表現の配列で、段の全体に一致したら落とす。例: `[":tenant\\?"]`)。落としたことを `rationale` に書く。`listed` で足す入口の `path` も、同じ段を落として書く
- 入口の id は、階層パスから記号を除いたもの。段の種類は「`_` + 1 文字」の印で表す: `:id` → `id_d`、`:tab?` や `:path(.*)?` → `tab_o` / `path_o`、URL が / だけの route → `root_r` (例: `/flows/edit/:namespace/:id` → `flows.edit.namespace_d.id_d`)。`listed` で足す入口の id も、同じ付け方にする
- 別の画面へ転送するだけの route (`redirect` だけで、`component` が無い) も、抽出器は拾う。入口のままにし、分析で「転送するだけ」と書く (承認のときに、人が `rejected` にしてもよい)
- どの URL にも当たらないときの画面 (`/:pathMatch(.*)`) も、入口にする
- 同じコンポーネントを指す route が 2 つ以上あっても、route ごとに入口にする (URL が違えば、渡る値が違う)

### 入れ子の route (`children`)

親の route のコンポーネントの中で、子のコンポーネントが描かれる作り (詳細の画面のタブなど)。このプロファイルでは、**子を入口にせず、親の画面に含める**。

- 親の画面を分析するとき、子の route のコンポーネントも、親から描かれるコンポーネントとして辿る
- 子の一覧は、親の入口の `summary` に書く (名前と `path`)
- 子が多く、1 件の分析が大きくなったとき (目安: フレームが 60 を超える) は、書き切ったうえで、報告に書く。そのリポジトリの入口の一覧で、子を `listed` の入口として分けるかを、人が決める

### アプリ全体の枠 (`shell`)

どの画面を開いても動く処理 (ログインの確認、設定やユーザーの読み込み、共通のメニュー) は、画面ごとに書かず、枠を入口として 1 回だけ分析する。抽出器は枠を拾わないので、**エージェントが `listed` で足す**。

| 枠にするもの | 見つけ方 | 階層パスと id |
|---|---|---|
| アプリの根のコンポーネント | `createApp(...)` に渡しているコンポーネント (`App.vue`) | `/(shell)/app`、`shell_s.app` |
| 共通のレイアウト | route の `meta.layout` や、根のコンポーネントが切り替えて描くレイアウト。データを読むものだけ | `/(shell)/layout/<名前>`、`shell_s.layout.<名前>` |
| 枠が描く共通の部品 | 根のコンポーネントや共通のレイアウトが、テンプレートに直接書いて描くコンポーネント (上のバー、メニュー、通知、再ログインの小窓、案内など) のうち、データを読む・外へ送るもの。1 つ = 入口 1 件 | `/(shell)/part/<名前>`、`shell_s.part.<名前>` |
| ルーターの共通の guard | `router.beforeEach` / `beforeResolve` / `afterEach` に渡している関数。データを読む・外へ送るものだけ | `/(shell)/guard`、`shell_s.guard` |

- レイアウトと部品の `<名前>` は、コンポーネントのファイル名から拡張子を除いたもの (例: `DefaultLayout.vue` → `DefaultLayout`)。置き場のフォルダ (`override/` など) は含めない
- 「テンプレートに直接書いて描く」には、後から読み込む部品 (`defineAsyncComponent`) と、`<component :is>` で描く部品も含める
- 共通のレイアウトは、部品を別の入口に分けた後、ファイル自身が API を呼ばなくなっても、**入口に残す** (どの部品を描くかを、入口の `summary` に書く場所になる)。入口にしないのは、API に至る部品を 1 つも描かないレイアウトだけ
- **共通の部品を、枠とは別の入口にする理由**: 枠を 1 件にまとめると、1 件の分析が大きくなりすぎる (実物で、フレームが 100 を超えた)。部品ごとに分けると、どの部品がどの API を呼ぶかも、一覧で見える
  - 根のコンポーネントと、共通のレイアウトの入口 (`app`、`layout/<名前>`) には、そのファイル自身が呼ぶ処理 (store の読み込み、計測の初期化など) だけを書く。別の入口にした部品は辿らず、部品の一覧を入口の `summary` に書く
  - 部品の `source` は、部品のファイルの 1 行目。`reason` に、どの枠が、どの行で描いているかを書く
  - 同じ部品を、2 つ以上の枠が描いているときも、入口は 1 件にする (`reason` に、描いている枠を並べる)
  - 部品の中で描かれる、さらに小さい部品は、分けない (部品の入口の中で辿る)
- 共通の guard は、いくつあっても**入口 1 件**にまとめる (どれも、画面を移るたびに続けて動くため)。`source` は、データを読む・外へ送る guard を登録している行 (`router.beforeEach(...)` などを呼んでいる行。関数を別の場所から渡していても、登録の呼び出しの行) のうち、ファイルのパスの辞書順でいちばん早いファイルの、いちばん小さい行。`reason` に、まとめた guard を、登録の場所 (ファイルと行) と一緒に並べる
- 「データを読む・外へ送る」に数えるもの: 描かれたときに呼ぶ API、利用者の操作 (ボタン、フォーム) で呼ぶ API、計測の送信。枠から 3〜4 段先の部品で初めて API に届くこともあるので、枠が描く部品を、API を呼ぶ所か見た目だけの部品に行き着くまで辿って確かめる (入口を見つけるときは、ここだけ深く読んでよい)
- 辿っても決められないときは、入口にする (承認のときに、人が外せる)
- 入口の層が 2 つあるので、`listed` を層ごとに分ける (`agent-listed-screen`、`agent-listed-shell`)
- データの読み書きにも外部への送信にも至らない枠 (見た目だけのレイアウト) は、入口にしない。確かめたことを `rationale` に書く
- どの画面がどの枠を通るかの関係は、このプロファイルでは持たない (一覧に `within` は付かない)。枠の入口の `summary` に、どの画面で動くかを書く

## 入口ごとの分析で見るもの

| 層 | 読む場所 | 拾うこと |
|---|---|---|
| screen | route の定義と、`component` のファイル | 描画するコンポーネント、URL のパラメータ、route ごとの guard (`beforeEnter`)、`meta` のうちデータの読み込みに効くもの |
| shell | 枠のファイル (根のコンポーネント、共通のレイアウト、共通の部品、共通の guard) | そのファイル自身が呼ぶ store と API。別の入口にした共通の部品と、`<router-view>` の中身は読まない |
| component | コンポーネントと composable のファイル | 子のコンポーネント、呼ぶ composable と store の関数、書き込み (作成・更新・削除) を起こす操作 |
| store | store のファイル | action が呼ぶ API の関数、別の store の呼び出し |
| api_client | HTTP を包む自前の関数のファイル | URL の形、HTTP メソッド、共通の接頭辞 |

### フレームにするもの・しないもの

- **フレームにする**: バックエンドの API の呼び出しに至る経路の上にある、コンポーネント、composable、store、API を包む関数
- **フレームにしない**: 見た目だけの部品 (ボタン、表の枠、アイコン、UI ライブラリの部品)、翻訳・日付・書式の小道具、型定義。経路の上に無いものは、`summary` で触れるだけでよい
- **同じファイルの中の、外に出していない補助の関数**は、フレームにしない。呼び出し元のフレームの中の処理として扱い、API に至るなら、呼び出し元の `call` や I/O の根拠に、その行も書く
- **store は、呼ばれる関数ごとに分ける**。store のファイル 1 つに、多くの action がある。画面が呼ぶ action だけをフレームにし、`name` に `<store の名前>.<action>` と書く。呼ばない action は書かない
- **画面と、アプリ全体の枠**: 画面を分析するとき、枠 (App.vue、共通のレイアウト、共通の guard) と、そこから描かれる部品は**辿らない**。枠が描く部品と同じ部品を、画面も自分で描いているときは、画面の側にも書く
- **`external` フレームの場所 (`source`)**: `source` には、**ライブラリや SDK の関数を実際に呼んでいる行**を書く。import の行を `source` にしない
- **SDK や部品のライブラリのソースが、範囲 (scope) の中にあるとき** (同じリポジトリの `packages/` に、生成された SDK や、見た目の部品のライブラリを持つ作り): それでも、生成された SDK の関数は `external` フレームで閉じる (`source` は呼んでいる行)。SDK の中は、フレームにしない。URL は、SDK のソースを読んで書く (下の「データの当てはめ」)。見た目の部品のライブラリは、「見た目だけの部品」として扱う (渡した関数を呼ぶ側になるときは、下の「関数を渡して、別の部品が呼ぶとき」)
- **子が `emit` で知らせ、同じファイルの補助の関数が受けるとき**: フレームにせず、知らせる行と、受ける関数の行を、その先の呼び出しの根拠に入れる (下の「関数を渡して、別の部品が呼ぶとき」が当たるのは、props や `provide` で関数を渡して、子が呼ぶときだけ)
- **フレームにしない子の部品や composable の中の、画面の遷移**: それを描く、いちばん近いフレームの `links` に書き、子の中の行を根拠にする
- **単一ファイルのコンポーネントで、「コードに書いてある順」**: template を先に、上から数える。その後に script
- **関数を渡して、別の部品が呼ぶとき** (props、`provide` / `inject`、設定に入れた関数、登録した関数を後で呼ぶ形): 渡された関数をフレームにし、`caller` は渡している側のフレーム。`call` は `interpretation` にし、根拠に、渡している行と、呼んでいる行 (読めれば) の両方を書く。呼ばれるかどうかが実行時の値で決まるときは、`unknown` + `dynamic_dispatch`
- **値の変化を見張って動く処理** (`watch`、`watchEffect`): 関数の呼び出しではないが、API に至るならフレームにする (見張りが、入口のファイルの外にあるとき。入口のファイルの中の見張りで、中身が同じファイルの補助の関数だけのときは、フレームにせず、見張りの行を、その先の呼び出しの根拠に足す)。`caller` は、見張っている値を変える側のフレーム。見張りが、入口のファイルの外 (store の中など) にあっても、入口の処理がその値を変えるなら、入口の経路に含める。`call` は `interpretation` にし、根拠に、見張りを書いた行を書く
- **実行時に通らない分岐** (この入口の木の中の呼び出し元が、固定の値を直接書いて、その分岐を閉じている): フレームにしない。条件と書く場所は、分析の skill の「固定の値で閉じている呼び出しは、辿らない」に従う (実行時の値で決まる分岐は、`conditional` で辿る)
- **条件付きで通る枝** (ダイアログを開いたとき、特定の URL のパラメータが付いたとき、特定の文字を打ったとき): 辿る。条件を、枝の最初のフレームの `summary` に書く。「時間が無い」を理由に、途中で打ち切らない
- **1 件が大きくなったとき** (目安: フレームが 60 を超える。画面でも枠でも): 止めずに書き切る。入口の `notes` と報告に、フレームの数と、分ける候補 (入れ子の route、ダイアログの先の枝、枠が描く共通の部品) を書く。分けるかは、人が決める
- **終端の決まり**: 機械チェックは、終端のフレーム (誰からも呼ばれないフレーム) が「`external` の層」「I/O を持つ」「業務のルールを持つ」「権限の確認を持つ」「行き先が入口の一覧にあるつながり (`embed` / `trigger`) を持つ」「`unknown` の主張を持つ」のどれかであることを求める。どれにも当たらない経路は、API の呼び出しか `external` まで書き切る (確認だけをする段や、業務のルールだけの段の先に、無い呼び出しを足さない)
- **API に届かない画面** (別の画面へ転送するだけ、固定の文言を出すだけ): 入口のフレームから、それが最後に頼るライブラリ (転送なら `vue-router`) を `external` フレームとして 1 つ書いて閉じる。I/O は無し。「API を呼ばない」ことは、入口の `summary` に書く

### 登録表から選ばれて描かれる部品 (`part`)

画面が、**保存された設定** (サーバーに保存した画面の構成、利用者が選んだ部品の種類) で、描く部品を決める作りがある。コードには、名前から部品を引く**登録表** (種類の名前 → コンポーネントの対応表。`<component :is="registry[type]">` で描く) があり、どの部品が描かれるかは、実行時の値で決まる。候補をすべて 1 つの画面の中で辿ると、1 件の分析がとても大きくなり、同じ部品を、登録表を使う画面の数だけ繰り返すことになる。

そこで、**部品を、部品ごとに別の入口に分けられる**。分けるかどうかは、入口の一覧で決まる。

| 入口の一覧 | 画面の分析 |
|---|---|
| その登録表の部品が、`part` の入口として入っている | 画面は、登録表を引くフレームで止める。部品は、部品の入口で分析する |
| 入っていない | これまでどおり、候補が有限で全部読めるなら、画面の中で、それぞれをフレームにする |

**入口を発見するとき**:

- 登録表を見つける (種類の名前からコンポーネントを引く対応表のうち、**保存された値** (サーバーに保存した構成、保存の前に利用者が選んでいる最中の値) で引くもの)。保存された値には、サーバーが返す定義 (プラグインの定義、型の情報) から決まる値も含める。キーをコードが組み立てるときは、組み立てた後の値をキーにする。登録表かどうかは、登録表を引くコードで決める (保存された値で引く画面が 1 つでもあれば、登録表)。URL の段や、画面の中の切り替え (タブ) で引く対応表は、登録表に当たらない (経路の表なので、画面の中で辿る)。対応表が、コードではなく、ファイルの置き場から作られること (`import.meta.glob`、プラグインの登録) もある。そのときは、項目 1 つ = ファイル 1 つとして数える
- 候補のうち、API を呼ぶ・外へ送る部品が **3 つ以上**あれば、部品を入口に分ける。2 つ以下なら分けない。迷うときは分け、迷ったことを `reason` に書く (承認のときに、人が外せる)
- 登録表の項目 1 つ = 入口 1 件。`abatlas-extract listed` で足す (抽出器の名前は `agent-listed-part`、`layer: part`)
  - 階層パスは `/(part)/<登録表の名前>/<選ぶときの名前>`、id は `part_p.<登録表の名前>.<選ぶときの名前>` (id では、画面の id と同じく、名前の中の `_` を 2 つ重ね、`-` のほかの記号を除く。キーが `.` で区切った完全な名前 (クラスの名前) でも、短くしない。登録表の中で一意であることを優先する)
  - 「登録表の名前」は、登録表を定義しているファイルの名前から、拡張子を除いたもの。1 つのファイルに登録表が 2 つ以上あるときだけ、変数の名前を使う。ファイルの置き場から作られる対応表では、対応表を作っているファイルの名前
  - 「選ぶときの名前」は、登録表のキー (保存された設定に入る値)。コンポーネントの名前と違うときも、キーを使う
  - `source` は、登録表の、その項目の始まりの行 (ファイルの置き場から作られる対応表では、部品のファイルの 1 行目)。`reason` に、どの登録表の項目か、どの画面が、登録表から部品を引いて描くか (ファイルと行) を書く
- API を呼ばず、外へも送らない部品 (文字を出すだけなど) は、入口にしない。確かめたことを、抽出器の `rationale` に書く
- **既にある入口と同じ部品**: 対応表の項目が指すコンポーネントが、既にある画面の入口の本体と同じ (route の `component` に書いたコンポーネント) なら、新しい `part` を作らない。描く側の画面は、その画面の入口を `embed` で指す
- **部品の入口にしたコンポーネントを、登録表を通さずに、直接描く画面もあるとき** (import して、そのまま描く): その画面でも、部品を辿らない。描くフレームの `links` に、`kind: embed` (`status: fact`。根拠は、描いている行) で、部品の入口を指す。部品の入口を足したときは、その画面も分析し直す
- **同じ登録表を、コードに書いた固定の値で引く画面** (既定の構成を渡して描く): 渡す種類の部品だけを `embed` で書く (`status: fact`。根拠は、固定の値を書いた行)
- 枠が描く共通の部品 (`/(shell)/part/<名前>`) は、この節の部品ではない (登録表から選ばれるのではなく、いつも描かれる)。これまでどおり `shell` の入口にする
- 部品の入口を足した・外したときは、登録表から部品を引いて**描く**画面の結果が古くなる。報告に、分析し直す画面を書く

**画面 (や枠) を分析するとき** (登録表の部品が、入口の一覧に入っているとき):

- 登録表を引くフレーム (登録表から部品を引いて描く component) までを書き、**その先の部品は辿らない**。登録表を引くフレームは、`<component :is="…">` を書いたコンポーネントのフレーム (その行だけを、別のフレームにしない)。そのコンポーネント自身の API の呼び出しは、ふつうに辿る
- 入口の一覧の状態 (approved / candidate) によらず、`part` の入口になっている項目を、すべて `embed` で書く
- 描いた部品が、外へ出している関数 (`defineExpose`) を呼ぶ所は、部品の中として辿らず、`summary` に書く。それを使って、描く側が呼ぶ API は、描く側の入口で書く
- そのフレームの `links` に、入口になっている部品を 1 件ずつ書く: `kind: embed`、`target` は選ぶときの名前 (登録表のキー)、`entry_id` は部品の入口の id。`embed` では、`entry_id` を必ず書く (機械チェックが、入口の一覧と照合する)。部品は実行時の値で選ばれるので、`status` は `interpretation` (根拠は、登録表を引く行と、登録表の項目の行)
- どの値で部品が選ばれるか (保存された設定のどの項目か) を、そのフレームの `summary` に書く。入口にしなかった部品は、`summary` に名前を書くだけでよい
- 登録表を引くフレームは、読み書きを持たなくても終端にできる (`embed` のつながりがあるため)

**部品 (`part`) を分析するとき**:

- 入口のフレームは、登録表の項目が指すコンポーネント (`layer: part`)。入口のフレームの `source` は、コンポーネントの定義の行 (単一ファイルのコンポーネント (`.vue`) では、ファイルの 1 行目。結果の `entry.source` は、入口の一覧のまま)。そこから、画面と同じ基準で終端まで辿る
- 部品を描く側 (画面、登録表を引くコンポーネント、枠) は辿らない。描く側から受け取る値 (props、`provide` された値、描く画面の URL から読む値、アプリの状態から読む値) は、入口のフレームの `parameters` に書く。入口のファイルではなく、呼んでいる composable が読むときも、入口のフレームの `parameters` に書く (根拠は、読んでいる行)
- 登録表を引くフレーム (描く側) が、部品を描く前に確かめている条件 (例: 対象の id が無ければ描かない) は、部品の入口の前提として使ってよい (`parameters` の `note` に、描く側の行と一緒に書く)
- 応答の行の項目が、保存された定義で実行時に決まるときは、コードが固定の名前で読む項目と、応答の型の項目だけを `fields` に書く
- 描く側が渡す値で動きが変わるとき (ある設定を渡したときだけ読む) は、候補をすべて辿り、`conditional` にして条件を書く。「どの画面も、その値を渡さない」ことは、部品の入口からは決められないので、理由にしない (分析の skill の「固定の値で閉じている呼び出し」に当たるのは、部品の木の中のコードが、固定の値を直接書いているときだけ)
- 権限の確認、設定、業務のルールは、部品の経路の上にあるものを、部品の結果に書く (描く側の結果には書かない)

### 多くの入口が描く、大きな部品 (共有の部品)

登録表から選ばれる部品のほかに、多くの画面が自分で描く大きな部品も、別の入口 (`part`) に分けられる。決まりは、`ui-nextjs` の `context.md` の「多くの入口が描く、大きな部品 (共有の部品)」と同じ。

- 候補は、数件を分析した後に、集計表「別の入口に分ける候補」から選ぶ (3 件以上の入口が通り、下に 10 以上の段を持つ、層が `component` の処理)。store の action や、API を呼ぶ関数は、分けない
- 階層パスは `/(part)/_shared/<コンポーネントの名前>`、id は `part_p.shared_a.<コンポーネントの名前>`。`source` は、コンポーネントのファイルの 1 行目。名前が、別のファイルの部品と重なるときは、置き場のフォルダの名前を、頭を大文字にして、前につなぐ (例: `charts/Legend` と `maps/Legend` は、`ChartsLegend` と `MapsLegend`)。それでも重なるときは、重ならなくなるまで、さらに上のフォルダの名前を、順に前につなぐ (例: `admin/charts/Legend` は `AdminChartsLegend`)。
- 描く側は、その部品を描くフレームで止め、`links` に `kind: embed` (`status: fact`。根拠は、描いている行) を書く。枠が描く共通の部品 (`/(shell)/part/<名前>`) は、これまでどおり `shell` の入口

### 同じ処理が何度も呼ばれるとき

1 つの入口の中で、同じ処理 (定義の行が同じ関数・コンポーネント・composable・store の action。`external` フレームなら、ライブラリを呼んでいる同じ行) が、複数の呼び出し元から呼ばれることがある。フレームは木 (`caller` は 1 つ) なので、次のように書く。

- その処理と、そこから先の経路は、**呼び出し元 1 つの下に 1 回だけ**書く。どの呼び出し元の下に書くかは、**入口から辿る順**で決める: 入口のフレームから、呼び出しを、コードに書いてある順 (同じ関数の中では行の順、同じ行なら左から) に、深さ優先で辿り、最初にその処理に着いた呼び出し元の下に書く (実際に動く順に近い木になり、分析者が違っても同じ木になる)
- それ以外の呼び出し元では、フレームを足さない。呼び出し元の `summary` に「<処理の名前> も呼ぶ。経路はフレーム `<id>` と同じ」と書く
- フレームを足さないと呼び出し元が終端になり、終端の決まりを満たせないときだけ、呼び先のうち、コードに書いてある順でいちばん早い 1 つを、その呼び出し元の下に、もう一度書く。書くのは、終端の決まりを満たす最初のフレーム (読み書きを持つフレームか、`external` のフレーム) まででよい。もう一度書いたフレームには、権限の確認・設定・業務のルールを繰り返さない (最初に書いたフレームだけに書く) (例外は 1 つ: もう一度書く呼び先が、読み書きにも `external` のフレームにも進まず、`rules` か `guards` だけで終端の決まりを満たしている、判定や確認だけの関数のときは、写しにも、その `rules` か `guards` を書く。分析の skill の「もう一度書いたフレームには、…繰り返さない」の例外)

## 事実・解釈・不明の付け方

- **fact**: コードにそのまま書いてある (import と呼び出し、URL の文字列、SDK の関数の名前)。根拠はその行
- **interpretation**: 読み取って要約したもの (フレームの summary、何のための処理か)。根拠は読んだ範囲の代表行
- **unknown**: 次の典型例ではこの理由を使う
  - 描くコンポーネントや、呼ぶ API が、実行時の値で決まる (動的なコンポーネント、名前で引く処理) → `dynamic_dispatch`
  - サーバーの応答や設定から、画面の作りや問い合わせの中身を組み立てる → `generated_at_runtime`
  - 送り先のホストや URL が、別の API の応答や、実行環境の設定で決まり、値がリポジトリに無い (例: 計測のサービスの送り先を、設定の API から受け取る) → `not_traceable_in_repo`
  - 呼び先が scope の外、または別のパッケージ → `out_of_scope`
  - 配布物だけでソースが無い → `binary_or_vendored`

## データの当てはめ

このプロファイルの対象は、ブラウザで動く画面だけである。データの読み書きは、すべてバックエンドの API の呼び出しとして現れる。

- **I/O を書くフレーム**: HTTP のライブラリや SDK を呼んでいる行の、`external` フレームに書く。共通の関数 (例: `fetch` を包む 1 つの関数) を、呼び出し元ごとに違う URL で呼ぶときは、同じ行でも「同じ処理」として省かず、**URL ごとに `external` フレームを分ける** (`name` に URL を書く)。ライブラリを使わない読み込み (`new Image().src` に URL を入れる) は、その行のあるフレームの I/O に書く (メソッドは `GET`、`interpretation`)
- バックエンドの API の呼び出し → `external_api` (`op: call`)。段は `host` と `path`
  - `host`: 画面と同じ配信元のバックエンドなら、`(backend)` と書く。接続先が環境変数で決まることだけを理由に、`unknown` にしない。他社のサービスなら、そのホスト名
  - `path`: `<HTTP メソッド> <URL の形>` (例: `GET /api/v1/flows/{id}`)。組み立て式の変数の部分は、`{名前}` にする。共通の接頭辞 (`/api/v1` など) は、付ける場所を 1 度読んで、付けた形で書く
  - 読むか書くかは、HTTP メソッドで分かるので、`note` に、何を読む・書くかを 1 文で書く
- **生成された SDK の関数を呼ぶとき**: SDK のソースが範囲の中にあれば、そこから URL を読んで、上の形で書く (`fact`。根拠に、呼んでいる行と、SDK の中で URL を書いた行の両方)。SDK が実行時に入れる段 (テナントなど) は、`{名前}` のまま書く
- **SDK のソースが範囲に無く、URL がリポジトリに無いとき** (SDK が、依存のパッケージにある): `path` に `sdk:<モジュール>.<関数>` と書く (例: `sdk:logs.searchLogs`)。SDK の関数を呼んでいることはコードにあるので、`fact`。URL を推測で書かない
- サーバーからの通知を受け続ける接続 (Server-Sent Events、WebSocket) → `external_api` (`op: call`)。`note` に「受け続ける」と書く
- ブラウザの中の保存 (localStorage、sessionStorage、cookie の読み書き) は、サーバーのデータではないので、**I/O に書かない**。画面の動きに効くなら、そのフレームの `summary` に書く
- 計測や分析のための、他社のサービスへの送信 → `external_api`。ホスト名がコードにあれば書く
