# cli プロファイル: エージェント向けの説明

対象は「コマンドラインから起動する道具」。ジョブスケジューラや運用者や別のプログラムが、コマンドとして起動するもの。入口の発見と、入口ごとの分析で、このファイルと `profile.yaml` の両方を読む。

Kestra のフロー定義から起動されるバッチは `batch-kestra`、画面を持つシステムは `ui-*` のプロファイルを使う。スケジューラの定義がリポジトリに無く、「呼ばれる側のコマンド」だけがある対象は、このプロファイル。

## アーキテクチャと層の連鎖

```text
command  (起動されるコマンド、サブコマンド。入口)
  → logic    (処理の手順と、業務の決まり)
    → adapter  (データや外部とのやり取りを受け持つコード)
      → external (外部のコマンド、ライブラリ、SDK。ここで終端)
```

層は、**役割**で分ける。言語や、フォルダの名前では分けない。

| 層 | 当てはめるもの | 例 |
|---|---|---|
| `command` | 起動されるファイルと、引数を解釈して処理を選ぶ所 | `bin/tool.sh`、`main()`、サブコマンドの定義 |
| `logic` | 処理の手順、業務の決まり、値の検査や変換 | usecase、domain、service、純粋な関数 |
| `adapter` | データの出し入れ、外部の呼び出しを包むコード | repository、gateway、DB や HTTP のクライアントを包む関数、設定ファイルを読む関数 |
| `external` | リポジトリに定義が無いもの | `psql`、`ssh`、`curl`、`jq`、ライブラリ、SDK |

- 対象が、層をフォルダで分けていれば (例: `presentation` / `usecase` / `domain` / `repository` / `gateway`)、対応を、分析リポジトリの `analysis-conventions.md` に書いてから分析する (入口ごとに当てはめがぶれないように)。目安: usecase と domain は `logic`、repository と gateway は `adapter`。presentation は、引数を解釈して処理を選ぶだけなら、入口のフレームに含める。業務の処理 (検査、変換、出力の組み立て) を自分で持つなら、入口の直下の `logic` のフレームにする。
- 層を分けていない小さな道具では、`logic` と `adapter` を無理に作らない。入口のフレームから、直接 `external` を呼んでよい。
- **フレームにする関数の目安**: 読み書きをする、外部を呼ぶ、業務のルール (判定、計算、検証) を持つ、のどれかに当たる関数。どれにも当たらない小さな補助 (文字の切り出し、空白を除く、表示の整形、行ごと・値ごとに呼ぶ変換) は、フレームにしない。フレームにしない関数が行う読み書き・設定・ルールは、それを呼ぶフレームに書く。
- 機械チェックは、誰も呼ばないフレーム (終端) に、次のどれかを求める: 外との境の層 (`external`) である、読み書きを持つ、業務のルールを持つ、不明の主張を持つ。判定や計算だけの関数 (domain の純粋な関数) は、`rules` を書けば、終端のフレームにできる。
- `external` が `role: boundary`。外部のコマンドやライブラリの呼び出しに達したら、閉じる。

## 入口の判別

入口 1 件 = **利用者が起動できる操作 1 つ**。

| 作り | 入口 | 見つけ方 |
|---|---|---|
| 実行ファイルが 1 つ 1 つの操作 | 実行ファイル 1 つ | 抽出器 `executables` (ファイル名の一致)。`files` を、実際の置き場に合わせる |
| 1 つの実行ファイルに、サブコマンドがある | サブコマンド 1 つ。サブコマンドを持たない実行ファイルは、それ自体 | サブコマンドの定義がコードにあるので、`ast` の抽出器で拾うか、読んで `listed` で足す |
| 1 つの実行ファイルが、どれか 1 つだけ選べるオプション (モード) で、別の処理に分かれる (例: `--check-a \| --check-b`) | サブコマンドと同じに扱い、モード 1 つを入口にする。処理の大半が共通で、オプションが動きを少し変えるだけなら、分けずに実行ファイル 1 つを入口にする | 読んで `listed` で足す |
| 起動用の薄いスクリプト (本体を `exec` するだけ) と、本体が分かれている | 起動用のスクリプトを入口にする | 抽出器 `executables`。本体は、入口のフレームから辿る |

- 階層パスは、置き場のまとまり (部品、パッケージ) とコマンドの名前。サブコマンドやモードは、実行ファイルの名前の下の段にする (例: `/tool/user/add`)。このとき、最後の段 (入口の名前) がサブコマンドになり、実行ファイルの名前は、まとまりの段になる。id は、段を `.` でつなぐ (抽出器の既定と同じ。例: `tool.user.add`)。
- サブコマンドやモードに分けた実行ファイルは、それ自体を入口にしない (同じ処理が 2 回数えられる)。抽出器 `executables` の `exclude` に、そのファイルを足す (ほかに一致するファイルが無くなるなら、`allow_empty: true` も足す)。
- `listed` で足すサブコマンドやモードの `source` は、その処理を選んでいる行 (`case` の枝、登録の行) にする。
- コマンドの一覧を定義したファイル (契約のファイル、ヘルプの定義、`package.json` の `bin`、`pyproject.toml` の `scripts`) があれば、抽出器が出した候補と突き合わせる。定義にあって実装が無いコマンドは、入口にしない (分析できるコードが無い)。`entry-list.yaml` の該当の抽出器の `rationale` に、その旨を書く。
- 入口にしないもの: テストだけが使うスクリプト、開発用の補助 (整形、検査、CI の中だけで使うもの)、`source` されるだけのファイル。利用者が起動する運用のコマンド (移行、掃除) は入口にする。
- 迷ったら入口にして、`reason` に迷った点を書く (人が `rejected` にできる)。

## 入口ごとの分析で見るもの

| 層 | 読む場所 | 拾うこと |
|---|---|---|
| command | 実行ファイルと、引数を解釈する所 | 引数とオプション (`parameters`)、読む環境変数、終了コードの決まり、標準出力・標準エラーに出すもの、呼び出す処理 |
| logic | 処理の関数、スクリプト | 呼び出しの順と条件、業務のルール、設定による切り替え |
| adapter | やり取りを包むコード | 接続先 (DB の database / table、ファイルのパス、相手のホスト)、操作、読み書きする列 |
| external | 外部のコマンドを呼んでいる行 | `source` は、その行。読み書きは、呼び出し元 (adapter か logic) のフレームに書く |

シェルの呼び出しの読み方:

| 書き方 | 扱い |
|---|---|
| `source file` / `. file` で読み込んだファイルの関数を呼ぶ | 関数ごとにフレーム (`kind: function`。上の「フレームにする関数の目安」に当たるものだけ)。読み込むだけの行は、フレームにしない |
| 別のスクリプトを起動する (`bash x.sh`、`./x.sh`、`exec x.sh`) | スクリプトをフレーム (`kind: script`)。起動した先が、入口の一覧にある別の入口なら、フレームにせず `links` (`kind: trigger`) に書く |
| バックグラウンドで起動する (`&`、`nohup`、`setsid`) | 上と同じ。`call` の `note` に、待たずに進むか、後で終わりを待つ (`wait`) かを書く |
| 同じ機械の、リポジトリに無い実行ファイルを起動する (設定に書かれたコマンド、別の製品のコマンド) | `external` のフレームにする。読み書きには書かない (相手が何を読み書きするかは、ここからは分からない) |
| `ssh host command` で、別の機械のコマンドを起動する | `ssh` を `external` のフレームにし、呼び出し元に `external_api` の読み書きを書く (host = 相手の機械、path = 起動するコマンド)。相手のコマンドが同じリポジトリにあっても、ここでは辿らない (`links` に書く) |
| パイプでつないだ外部のコマンド (`psql ... \| jq ...`) | 別のプロセスやサービスに届くコマンド (`psql`、`ssh`、`curl`、`aws`) を `external` のフレームにする。整形だけのコマンド (`jq`、`sed`、`awk`、`grep`、`sort`、`tr`) は、フレームにしない |
| ファイルを直接読み書きする (リダイレクト `< file` `> file`、`while read ... < file`、`cat file`、`sed ... file`、`cp`、`mv`、`rm`、`mktemp`) | `external` のフレームにしない。そのフレームの `io` (`filesystem`) に書く。操作の当てはめは、下の「データの当てはめ」 |
| 待つ・止めるだけのコマンド (`sleep`、`kill`、`wait`) | フレームにも、読み書きにも書かない (動きに関わるなら、`summary` に書く) |
| `trap` で登録した処理 | 終了のときに必ず動くもの (`EXIT`) は `when: always`、失敗のときだけ動くもの (`ERR`、終了コードを見て分ける) は `when: on_failure`、シグナル (`HUP` / `INT` / `TERM`) で動くものは `when: conditional` (`condition` に、どのシグナルか) |
| `eval` | 実行する文字列が、読めば決まる (保存しておいた `trap` を戻すだけ、など) なら、ふつうの処理として読む。実行時に組み立てた文字列を実行するなら `generated_at_runtime` |
| `set -e` の下で、失敗したら止まる | 呼び出しは `always` のまま。失敗のときに何もしない所は、書かない |
| 直前のコマンドが成功したときだけ続ける (`a && b`、成功を確かめる `if`) | `b` は `always` (失敗による打ち切りの裏返しで、分かれ道ではない) |
| 入力の誤りを見つけて、早く返す (戻り値が 0 でも 0 以外でも) | その後ろの呼び出しは `always` (打ち切り)。「成功として早く返す」(`conditional`) に当たるのは、業務の分かれ道で、処理を終えて返すときだけ |

- 同じ関数が、1 つの入口の中で複数の所から呼ばれるときは、入口から、コードに書いてある順に深さ優先で辿って、最初に着いた呼び出し元の下に 1 回だけ書く。ほかの呼び出し元は、`summary` に「<関数> も呼ぶ。経路はフレーム `<id>` と同じ」と書く。そうすると呼び出し元が終端になり、上の終端の決まり (機械チェック) を満たせないときだけ、読み書きを持つ最初のフレームまで、もう一度書く。
- 終了コードの決まり (どの場合に、どの値で終わるか) は、業務のルール (`rules`、`kind: decision`) として、決めている段に書く。呼び出す側 (スケジューラ) との約束になるため。

## 事実・解釈・不明の付け方

- **fact**: コードにそのまま書いてある (`psql -c "INSERT INTO runs ..."`、`cat "$CONFIG"`)。根拠はその行
- **interpretation**: 読み取って要約したもの (フレームの `summary`)。変数を 2 段以上たどって決めた接続先。確かめるだけの読み取り (`[ -f "$path" ]`) で、パスを変数からたどって決めたもの
- **unknown**: 次の典型例では、この理由を使う
  - 接続先やパスが環境変数や設定ファイルで決まり、値がリポジトリに無い → `not_traceable_in_repo` (分かる段だけ書く。変数の名前を `note` に書き、`settings` にも書く)
  - 起動するコマンドが、引数や設定の値で決まる (`"$RUNNER" "$@"`、設定ファイルに書かれたコマンド) → `dynamic_dispatch`
  - `eval` や、実行時に組み立てた文字列を実行する → `generated_at_runtime`
  - 起動する先が、範囲の外か、別のリポジトリ → `out_of_scope`
  - ソースの無い実行ファイル → `binary_or_vendored`

## データの当てはめ

- RDB (`psql`、`mysql`、`sqlite3`、ドライバ) → `rdb`。接続先が変数なら host は書かず、database / schema / table を SQL から書く。テーブルをキューとして使っていても、`rdb` のまま (`queue` にしない。使い方は、フレームの `summary` と、状態の列の `set_to` で分かる)
- ファイル (設定、実行の記録、ロック) → `filesystem`。パスが変数で組み立てられるときは、変わる所を `{名前}` にする (例: `runs/{run_id}/spec.json`)。パスが引数で決まるときは、引数の名前を `{名前}` にする (例: `--config <path>` なら `{config}`)

  | シェルの操作 | `op` |
  |---|---|
  | 中身を読む (`cat`、`< file`、`source`) | `read` |
  | 作る・上書きする (`> file`、`cp` の写し先) | `write` |
  | 追記する (`>> file`) | `append` |
  | 消す (`rm`) | `delete` |
  | あるか・種類・権限を確かめるだけ (`[ -e ]`、`[ -f ]`、`[ -r ]`、`[ -x ]`、`ls`) | `list` |
  | 名前を付け替える・移す (`mv`) | 移す前の名前の `delete` と、移した後の名前の `write` |

- その処理の中だけで作って消す一時ファイル (`mktemp`) は、読み書きに書かない。元のファイルを一時ファイルに写してから読む作りでは、列 (`fields`) は、元のファイルの読み取りに書く
- 検査や変換の対象として読むファイルの中の項目 (例: 検証する設定ファイルのキー) は、`fields` に書く (`settings` ではない。`settings` は、この道具自身の動きを変える設定)
- 読むが、この入口の動きを変えない環境変数 (置き場を指すだけ、など) は、`settings` ではなく、入口のフレームの `parameters` に書く
- 既定の場所と、設定で指定した場所の、どちらか一方を読み書きする作りは、読み書きを 1 件にし、パスの変わる所を `{名前}` にして、`note` に既定の値を書く
- 標準出力・標準エラーは、読み書きに書かない。出力の形が、呼び出す側との約束になっているとき (キーの並び、行の数) は、入口のフレームの `summary` と、決めている段の `rules` に書く
- 別の機械やサービス (`ssh`、`curl`、API) → `external_api` (`op: call`。host は相手、path は起動するコマンドか URL の形)
- メッセージ基盤 (Kafka、SQS など) → `queue`
