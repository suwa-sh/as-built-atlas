# 文書を書く・直す

守ることは `docs/rules/docs.md`。全体の流れは skill `dev-change` に従う。

## 1. どこに書くかを決める

| 書きたいこと | 置き場 |
|---|---|
| 決定の経緯 (なぜそう決めたか、捨てた案) | `docs/adr/NNNN-<slug>.md` を 1 つ足し、`docs/adr/README.md` の表に 1 行 |
| 使う人の手順 (人がやること、裏で動くもの、手に入るもの) | `docs/guide/` の、場面のファイル |
| いま守る状態 (仕組みと、その理由) | `docs/architecture/` の、主題のファイル |
| 正確な仕様 (項目、コマンド、集計表、プロファイルごとの決まり) | `docs/reference/` の、主題のファイル |
| 開発で守ること | `docs/rules/` の、部分のファイル |
| 画面の見た目の決まり | `DESIGN.md` |
| 作業のこつ、はまり所 (エージェントだけが読む) | `.agents/memory/` |

決定を変えたときは、2 つを同じ変更で行う。

1. 新しい ADR を足す。古い ADR の状態を「置き換え済み (→ 新しい番号)」にする。古い ADR の本文は書き換えない。
2. `docs/` を、最新の状態に書き換える。経緯は書かず、ADR を指す。

ADR の型は、`docs/adr/` の既にあるファイルに合わせる: 状態、記録した日、背景、決定、捨てた案 (表)、結果。

## 2. 書く

1. `docs/rules/docs.md` の「書き方」と「図 (mermaid)」を読む。
2. 書く事実 (コマンド、項目の名前、上限の数、ファイルの名前) を、実装を読んで確かめる。覚えで書かない。
3. 書く。呼び名に迷ったら、`docs/architecture/README.md` の「言葉」の表を見る。
4. 書いた後に、長い段落と、図にできる説明が残っていないかを読み返す。

## 3. 確かめる

```bash
uv run --locked python .agents/skills/dev-docs/scripts/check_docs.py
```

| 検査 | 内容 |
|---|---|
| リンク切れ | ルートの Markdown、`docs/` 内の Markdown、見本の README (`examples/*/README.md`) の相対リンクの先が、実在するか |
| 配布先で切れるリンク | 配る置き場 (`docs/architecture/`、`docs/guide/`、`docs/reference/`) から、その外へのリンク (分析リポジトリには、この 3 つだけが配られる) |
| mermaid の危ない書き方 | 引用符で包んでいない、かっこ・スラッシュ |
| mermaid を実際に描く | `mmdc` があれば、全部の図を描く。無ければ、その旨を出す (描いていないと報告する) |

続けて、手で確かめる。

| 確かめること | やり方 |
|---|---|
| ほかからの参照 | 文書を動かした・分けた・節の名前を変えたときは、古い名前を、skill (`.agents/skills/`)、`AGENTS.md`、`.agents/memory/`、`tests/` で探す |
| 手順が動く | 書いたコマンドを、実際に実行する。手順の順番 (例: 分析し直してから集計する) を、実装の動きと照らす |
| 図の見た目 | 描いた図を、何枚か開いて見る |
| 画像 | 画面の見た目を変えたなら、skill `dev-sample-regen` で撮り直す |

## 4. 外部レビュー

文書も、別系統のレビュアーに見てもらう。観点の例:

| 観点 | 見ること |
|---|---|
| 事実の正確さ | 記述が、今の実装と合っているか |
| 元の文書からの抜け | 書き直しで、判断に効く事実が消えていないか |
| 参照の整合 | ほかからの参照が、辿れるか |
| 手順の再現性 | 書いてあるとおりに実行して、動くか |
| 言葉の一貫性 | 同じものを、違う名前で呼んでいないか |
