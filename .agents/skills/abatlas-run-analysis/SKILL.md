# 今回の分析を取りまとめる

分析リポジトリで実行する。以下の `<abatlas>` は `docker compose run --rm abatlas`。対象、プロファイル、分析モデルは作業定義から読む。

## 全体案を準備する

1. 初回は `abatlas-discover-entries` で入口を調べる。差分更新では対象の版を合わせ、`impact . --from <前回の分析コミット> --json` で変更ファイル、入口、根拠、以前の呼び出しを読む。新しい登録・設定・動的な呼び出しが既存の根拠に出ていないか調べる。以前の分析を更新するときは差分更新を使う。初回の途中で規約が変わった場合は、同じ対象版で `--initial` の案を作り直す。
2. `analysis/batch-draft.yaml` に下書きする。`assessment` には実際に読んだ変更と、再利用できる理由を書く。初回は入口をどう調べたかを書く。`decisions` では候補の採否と追加の再分析を理由付きで指定する。根拠が同じ入口はまとめる。情報不足なら先に自分で追加調査する。解消できなかった業務上の判断だけを `questions` に残す。一つの回答が複数の入口に効く場合は一問にまとめる。

   ```yaml
   assessment: 決済ジョブ末尾の注釈を確認。起動設定・呼び出しの追加はなく、既存の他の入口には影響しない。
   decisions: []
   questions:
     - entries: [manual.retry_settlement]
       question: 手動の再決済フローを本番運用で使いますか？
   ```

3. 回答を得たら該当の質問に `answer` を残す。上の例で「本番で使う」なら `decisions` に `{entries: [manual.retry_settlement], action: include, reason: 障害時に運用者が本番で起動する}` を足す。検証専用なら `exclude`。調査依頼は未回答のまま調べ直す。影響が広がると分かった既存入口には `reanalyze` を使う。
4. `<abatlas> propose . --from <前回の分析コミット> --draft analysis/batch-draft.yaml` を実行する。初回は `--from` の代わりに `--initial`。未整理の候補は自分で埋める。利用者には対象版、入口と作業の件数、再利用の理由、廃止対象、残った質問を示す。全件の内訳と根拠は必要なときに `--json` で見せる。分析モデルが未設定で実行に確認が要る場合は、この時点で今回のモデルも合わせて示す。
5. 質問がなくなった最新の案について人から全体の承認を一度受ける。事前に分析結果や入口の承認状態を書き換えない。回答だけを全体承認として扱わない。

## 承認から実行まで

1. 同じ引数で `propose` を `approve` に替え、`--plan-id <承認したID> --by <承認者>` を付けて実行する。確定で拒まれたら、新しい案の差分を示す。承認は入口の採否と作業一覧に同時に効き、再利用記録もここで確定する。
2. 出力の `jobs` にある `analyze`・`reanalyze` の各入口に `abatlas-analyze-entry` を実行する。少量なら直ちに開始する。複数入口は各1件を新しい分析担当に渡し、多ければまず2〜3件、残りは同時数を抑えて流す。共通差分は一度読み、対象版、変更内容、根拠行を各担当に渡す。入口ID・作業種別・再分析理由も渡す。人に入口ごとの再承認を求めない。分析規約そのものを変える必要が生じた場合は、影響した案を更新する。
3. `retire` は廃止作業として扱う。前回の分析コミットに旧結果を保全できていることとリンク元を確認し、承認された入口だけを現行の結果・レビュー・再利用記録から外す。未保全の編集が見つかったら個別に解決する。
4. 中断後は `<abatlas> queue . --plan-id <承認したID>` の残りから再開する。各担当の検査とレビューが完了し、残りが空になれば `<abatlas> build .` で集計する。
