# 入口 1 件の分析

入口 1 件につき YAML 1 ファイル。主張ごとに **事実 / 解釈 / 不明 + 理由** と根拠 (ファイルと行) を付ける。分からないことを分かったように書かない。

## 入力

- 分析リポジトリのルート (カレントディレクトリ)。`analysis/work-definition.yaml` と `analysis/entry-list.yaml` が必須
- 分析の資産は `analysis/` の下: `analysis/work-definition.yaml`、`analysis/entry-list.yaml`、`analysis/results/`、`analysis/reviews/`
- 入口 id (引数)。`analysis/entry-list.yaml` の `entries[]` で `status: approved` のもの
- OSS の参照物 `<oss>`: カレントディレクトリに `.abatlas/` があればそれ (分析リポジトリ)。無ければこの SKILL.md の実体の 3 つ上 (OSS の checkout)
- ツールの呼び方 `<abatlas>`: 分析リポジトリでは `docker compose run --rm abatlas` (コンテナの中で動く。パスはリポジトリのルートからの相対で書く)。OSS の checkout では `uv run abatlas`
- プロファイル: `analysis/work-definition.yaml` の `profile.dir`。無ければ `<oss>/profiles/<profile.id>/`
- 結果ファイル名 `<file>`: 入口 id の `/` を `__` に置き換えて `.yaml` を付けたもの (例: `daily/housekeeping` → `daily__housekeeping.yaml`、`daily.housekeeping` → `daily.housekeeping.yaml`)。ETL と機械チェックも同じ規則で探す
- 出力: `analysis/results/<file>`

## 前提

- 対象は `target.clone_path` に `target.commit` で checkout 済み (違えば止める)。分析リポジトリでは `.env` の `ABATLAS_TARGET` が同じ場所を指している (コンテナには `/ws/target` として見える)
- 冪等: `analysis/results/<file>` が既にあり、その `target.commit`・`analyzer.profile.version`・`analyzer.skill_version` (2 つ目の数字まで。3 つ目だけの違いは、同じと見る) が今回と同じで、テストとの対応の選択も同じ (作業定義の `analysis.tests` が `true` なら結果の `analyzer.tests` も `true`、そうでなければ結果に `analyzer.tests` が無いか `false`) なら、何もせず「skip」と報告して終わる。どれかが違えば、分析し直して、結果とレビューのファイルを置き換える

## 手順

1. **このリポジトリの癖を読む**: 分析リポジトリに `.agents/memory/desired-state/analysis-conventions.md` があれば最初に読み、以下の手順で `context.md` と食い違うときは**こちらを優先**する (unknown の扱い、データの当てはめ、見なくてよいもの)。無ければ飛ばす
2. 読む: `profile.yaml` (層の連鎖、各層の `invokes_next` と `io`)、`context.md` (分析で見るもの、事実・解釈・不明の付け方、データの当てはめ)、`<oss>/schema/vocab/unknown-reasons.yaml`、`<oss>/schema/vocab/resource-kinds.yaml`、見本 `<oss>/tests/fixtures/result-housekeeping.yaml`
3. 入口を特定する: `analysis/entry-list.yaml` の該当 entry の `source` と `attributes` を読む。`source.file` を開き、入口のフレーム (`caller: null`) を書く
4. 層の連鎖に沿って辿る。各フレームで次を決める:
   - `layer` (プロファイルの層 id)、`kind`、`name`、`source` (定義場所。`role: boundary` の層のフレームはリポジトリに定義が無いので、リポジトリの中でそれを使っている箇所。どの行にするかは `context.md` の決まりに従う)、`caller` (呼び出し元フレームの id)
   - `call`: 呼び出しが成立する根拠 (呼び出し箇所の file と line を evidence に)。`when` に、その呼び出しがいつ起きるかを書く

     | `when` | いつ | `condition` |
     |---|---|---|
     | `always` | 呼び出し元が動けば、必ず呼ぶ | 書かない |
     | `conditional` | 条件を満たすときだけ呼ぶ (if、繰り返しの中の絞り込み、設定や引数による切り替え、利用者の操作) | 条件を 1 文で書く (式をそのまま写さない。式は、根拠の行にある) |
     | `on_failure` | 呼び出し元の処理が失敗したときだけ呼ぶ (例外の処理、失敗の通知、後片付け、やり直し) | 何が失敗したときかを 1 文で書く |

     - 入口のフレーム (`caller: null`) には `call` が無いので、書かない。成功しても失敗しても動く後片付け (finally) は `always`
     - `always` は、「呼び出し元が、途中で打ち切られずに進めば、必ず呼ぶ」の意味。呼び出しの手前に、入力の誤り・権限の不足・相手が見つからないことで打ち切る経路 (早い return、例外) があるだけなら `always` (打ち切りは、`rules` や `guards` に書く)。打ち切るかどうかが設定で決まるとき (例: ある環境変数があれば何も描かない) は、その後ろの呼び出しを `conditional` にし、設定を `settings` に書く
     - 業務の分かれ道 (ある場合だけ行う処理) の中にある呼び出しは `conditional`。手前に「ある条件なら、成功として早く返す」経路 (例: 管理者なら、ここで許可して返す) があるときも、その後ろの呼び出しは `conditional`
     - if の中にあっても、この入口から辿る限り条件がいつも成り立つ呼び出しは `always`。そう判断した理由を `note` に書く。逆に、この入口からは条件が成り立たないように見える呼び出しは、消さずに `conditional` で書き、そう見える理由を `note` に書く (次の「固定の値で閉じている呼び出し」だけは別)
     - **固定の値で閉じている呼び出しは、辿らない**: 条件が、この入口の木の中の呼び出し元がコードに直接書いた固定の値 (リテラル。引数を渡さないことで効く既定値も含む) だけで決まり、決して成り立たない呼び出し (例: 親が `allowEdit={false}` と書いて子を描き、子は `allowEdit` のときだけ削除のボタンを描く)。その先はフレームにせず、条件を持つフレーム (例では子) の `summary` の `note` に、閉じている呼び出しの名前と、閉じている値と、値を渡している行を書く (フレームに `notes` の項目は無い)。当てはめるのは、次の 3 つをすべて確かめたときだけ。1 つでも確かめられなければ、上の決まりどおり `conditional` で書く
       - 値が、この入口の木の中のコードに直接書いてある (設定、保存されたデータ、状態、入口の外から受け取る値 (URL、描く側から渡される値、引数) で決まるものは、当たらない)
       - 条件が、その値だけで決まる (ほかの値との組み合わせで決まるなら、当たらない)
       - 条件を持つフレームに、この入口の木の中の別の呼び出し元から、別の値で着く経路が無い (あれば、閉じていない。その経路の下に書く)
     - 上の決まりの補足:
       - 条件が組み合わせのとき: `A && B` は、どちらか 1 つが固定の値で偽なら、閉じている。`A || B` は、すべてが固定の値で偽のときだけ、閉じている
       - 固定の値が、HTTP の要求 (クエリ、本文) を通って、サーバー側の分かれ道に効くとき (呼ぶ側が、そのパラメータをいつも付けない、いつも同じ値で付ける) も、木の中に直接書いた値として扱う。`note` に、呼ぶ側の行と、受ける側の条件の行を並べる
       - 閉じた分かれ道の中にだけある読み書き・業務のルール・設定は、書かない。1 つの文 (1 つの SQL) の中の、条件で通らない部分は、分けられないので残し、`note` に書く
       - 固定の値で、条件がいつも成り立つときは、上の決まりどおり `always` (閉じる側だけでなく、開く側も、固定の値で決める)
       - この入口の木の中に、呼び出し元が無い受け口 (ほかの入口だけが呼ぶ API) は、もともと書かない (閉じた呼び出しとは別)
     - 利用者の操作 (ボタン、送信) で動く処理は、その操作で最初に動く段を `conditional` にし、`condition` に操作を書く。描画のたびに動く準備の呼び出し (フックや composable の呼び出し) は `always`
     - 親が、子を描くかどうかを条件で決めるときは、子の段を `conditional` にする
   - `summary`: 何をする処理か (interpretation。読んだ範囲の代表行を evidence に)
   - `parameters`: 入力 (分かる範囲)
   - `io`: 読み書きするデータ。`resource.kind` と `levels`、そして `op`。**操作は種類ごとに決まっている** (`resource-kinds.yaml` の `kinds.<kind>.ops[].id`)。段の名前も同じファイルのとおり。読み書きの相手 (どの表、どのファイル、どの相手か) や操作が分からないときは、分かる段だけを書き、主張全体を `unknown` + `reason` にする。分からないのが、実行環境の設定で決まる接続先の段 (host、database など) だけで、プロファイルの `context.md` が「書かない」と決めているときは、その段を書かずに、状態はそのまま (`fact` / `interpretation`) でよい

     | 種類 | 操作 |
     |---|---|
     | rdb | create / read / update / delete |
     | kvs | get / set / delete / expire |
     | queue | publish / consume |
     | filesystem | read / write / append / delete / list |
     | object_storage | get / put / delete / list |
     | external_api | call |
   - `io[].fields`: その読み書きが触る列 (RDB の列、KVS やファイルの中の項目、外部 API へ送る・受け取る項目)。コードから読める範囲で書く
     - `name` は、データの側の名前 (ORM の属性名と列名の対応が範囲の中で読めれば、列名。読めなければ属性名のまま)
     - `use` は、`read` (値を読む) / `write` (値を書く) / `filter` (絞り込み・結合・並べ替えの条件に使う) のうち、当てはまるものすべて
     - 書くのは、**その読み書きがデータとやり取りする列** (問い合わせが取り出す列、書き込む列、条件に使う列)。取り出した後に、コードがどの列を使うかは見ない
     - 全部の列をやり取りするとき (`select *`、列を選ばずに行をまるごと取る ORM の呼び出し、行の削除) は、`name: "*"` を 1 つ書く (`use` は、読むなら `read`、行やキーを消す・まるごと書くなら `write`)。条件に使う列は、別に `filter` で書く
     - 書く値を決める式の中で読む列 (`set x = case when y ...` の `y`) は `read`。行を選ぶ条件 (`where`) に使う列は `filter`
     - 結合や、関連をたどる条件で使う列は、その列を持つデータの読み書きに `filter` で書く (関連の先のデータにも読み書きがあれば、そちらにも書く)
     - 列の名前が、この段ではなく呼び出し元でしか読めないとき (受け取った値をそのまま書く段) は、呼び出し元の行を根拠にしてよい
     - 状態を表す列に、決まった値を書くとき (例: `status = 'shipped'`) は、`set_to` にその値を書く
     - KVS やファイルのように、値をまるごと読み書きするデータでは、値の中の項目 (JSON のキーなど) がコードから読めれば項目の名前を書き、読めなければ `name: "*"` を書く
     - 列が読めないとき (動的に組み立てる SQL など) は、`fields` を書かず、`note` に理由を書く
   - `links`: この段から、**ほかの入口**へのつながり。`kind` は `navigate` (画面の遷移) / `trigger` (別のジョブ・フロー・処理の起動) / `overlay` (いまの画面に重ねて開く画面) / `embed` (この入口の中に描く、別の入口にした部品。プロファイルの `context.md` が、部品を別の入口に分けると決めているときだけ使う。`entry_id` を必ず書く)。`target` は、コードに書いてあるとおり (ルートの名前、URL の形、フローの id)。行き先が式で決まるときは、値が読める行き先を 1 件ずつ書き、読めない分は、式をそのまま `target` に書いて `unknown` にする。行き先が `analysis/entry-list.yaml` のどの入口かが分かれば、`entry_id` も書く。同じリポジトリの中の関数の呼び出しは、ここではなく `caller` で表す。外部の API は `io` に書く。呼び先を辿るか (フレームにするか) は、プロファイルの `context.md` の決まりのまま
   - `guards`: この段で行う権限の確認 (満たさなければ先へ進めない確認)。`kind` は `authentication` (ログイン済みか) / `role` (役割) / `permission` (操作の許可) / `ownership` (持ち主・所属か) / `other`。`value` に、求める値 (役割や権限の名前、持ち主の条件) をコードのとおりに書く。`role` / `permission` / `ownership` では、`unknown` でなければ必ず書く。`authentication` のように求める値が無い確認では、`value` を書かない。確認を**実際に行っている段** (満たすかどうかを判定している段。判定の結果を受けて止めるだけの呼び出し元ではない) に書く (呼び出し元ごとに繰り返さない)。ログインの処理そのもの (パスワードの照合) は、確認ではなく `rules` (`validation`) に書く。「ログイン済みなら別の画面へ移す」のような、先へ進むのを止めない分かれ道も、確認に書かない (`links` に書く)
   - `settings`: この段の動きを変える設定 (環境変数、機能の切り替え、設定ファイルの値)。`name`、`kind` (`env` / `feature_flag` / `config_file` / `remote` / `other`)、`effect` (動きがどう変わるか。`unknown` でなければ必ず書く)。設定を**読んで使っている段**に書く。値を右から左へ渡すだけの段には書かない。設定を読む関数が段になっていないとき (小さな補助の関数) は、その結果で動きを変える段に書く。同じ設定で動きが変わる段が複数あれば、段ごとに書いてよい (集計が、入口ごとにまとめる)。書くのは、処理の流れや、読み書きの相手 (接続先、置き場) を変える設定。値を与えるだけの秘密 (署名の鍵、パスワード) と、どの入口でも同じように効く接続の設定 (データベースの接続先など) は書かない。この入口では有無で結果が変わらない設定も書かない。名前は、実行する環境で設定する名前 (環境変数の名前) で書く。コードが読む名前と違うとき (設定ファイルが写している) は、写している行も根拠に入れる (両方の行が根拠にあれば `fact` でよい)
   - 権限の確認や業務のルールだけを書いて、フレームを閉じてよいのは、その関数が、確認や判定のほかに、読み書きも外への呼び出しもしないときだけ (機械チェックは、`guards` か `rules` を持つ終端を通すが、その先の辿り漏れは見つけない)
   - 秘密の値でも、有る無しで動く段が変わるもの (例: トークンが無ければ、外への送信の段を飛ばす) は `settings` に書く (値は書かない)。設定ファイルの中のキーは、`name` をキーの名前にし、ファイルは根拠の行で示す
   - `rules`: この段にある業務のルール。`kind` は `calculation` (計算) / `validation` (入力や状態の検証) / `decision` (処理を分ける判定)。`value` に内容を 1 文で書き (`unknown` でなければ必ず書く)、式や条件の行を根拠にする。業務の意味を持つものだけを書く (null の確認、型の変換、表示の整形、入力が空でないことだけの確認は書かない)。設定で分かれる処理は、`settings` だけに書く (`rules` に重ねない)。ルールが、段になっていない補助の関数にあるときは、それを呼ぶ段に書く
   - `tests`: `analysis/work-definition.yaml` の `analysis.tests` が `true` のときだけ。この段 (`source` の関数やスクリプト) を直接呼ぶテストを範囲の中で探し、`name` と `kind` (`unit` / `integration` / `e2e`) を書く。根拠は、テストの行。見つからなければ書かない。このとき、`analyzer.tests: true` を書く
   - 上の 5 つ (`links` / `guards` / `settings` / `rules` / `tests`) と `fields` は、見て無ければ書かない (空の並びを書かない)
   - **名前と値は、入口をまたいで同じ綴りになるように書く** (集計が、同じ綴りのものを 1 つにまとめる)
     - `guards[].value`、`settings[].name`、`links[].target`、`fields[].name`、`tests[].name` には、コードに書いてある文字 (識別子、式、文字列の値。行き先の URL やルートの名前、全部の列を表す `*` も、これに当たる) だけを書く。説明の文や、かっこ書きの補足を混ぜない (補足は `note` に書く)。例: `value: "user.isAdmin"` (「user.isAdmin (role が admin のユーザー)」とは書かない)
     - 同じものがコードの中で 2 通りに書かれているとき (例: `user.isAdmin` と `user.role === ROLES.admin`) は、定義の側の書き方 (値を決めている場所の式や定数の名前) にそろえる
     - 同じもの (同じ設定、同じ確認の関数、同じ列) が、ほかの入口の結果 (`analysis/results/` のほかのファイル) に既に書かれていれば、その綴りに合わせる。名前で探して確かめる
     - 分析リポジトリの `analysis-conventions.md` が、そろえる書き方を決めていれば、それに従う
   - 次の層の呼び出しを見つけたら、新しいフレームを足して `caller` で指す。`role: boundary` の層 (外部ライブラリ・SDK・CLI) に達したらそこで閉じる
5. 辿れないところは **unknown + reason** で明示する (`context.md` の典型例に従う)。推測で埋めない
   - `not_analyzed` (手順がそこまで届いていない) で止めるときは、`note` に「どこまで読んだか」と「なぜ止めたか」を書く (続きを分析するかを、人が決められるように)。打ち切ってよい範囲を、分析リポジトリの `analysis-conventions.md` やプロファイルの `context.md` が決めていれば、それに従う
6. `summary` (入口全体の概要) と `analyzer` (profile の id / version、`skill_version` はこの SKILL.md 末尾の版、`model` に使ったモデル、`analyzed_at` は結果を書き終えた時点の実際の時刻。`date -u +%Y-%m-%dT%H:%M:%SZ` で取り、見込みの時刻を書かない。レビューの後に結果を直したら、直し終えた時刻に書き換える) を書く。`target` は `analysis/work-definition.yaml` と同じ (`clone_path` も、そのまま写す。手元の絶対パスが入っていても、分析リポジトリの中の値なので、省かない。集計は、作業定義と違う `target` の結果を知らせる)
   - YAML の文字列 (summary の value、name、note、detail) は二重引用符で囲む。コロンや `#` を含む文章を裸で書くと読めなくなる
   - 結果のいちばん上の `notes` (任意) には、迷った点と選んだ扱い、直さなかったレビューの指摘と理由を書く。`notes` は、1 つの文字列 (並びにしない。項目は、文の中で (1) (2) のように分ける)
   - `summary` の根拠は、文の中の句ごとに、それを支える行を入れる (代表の 1 行だけにしない。レビューは、句ごとに根拠を確かめる)
   - `analyzer.run` (コスト・所要時間) は**書かない**。実行中のセッションは自身のコストを知れない。呼び出した側が後で書く
7. 機械チェック: `<abatlas> validate result analysis/results/<file> --work analysis/work-definition.yaml` (プロファイルは、作業定義の `profile.dir` から自動で読まれる。出力に「プロファイルを自動で読めない」と出たら、OK でも完了にしない (プロファイルとの突き合わせが省かれている)。`analysis/work-definition.yaml` の `profile.dir` と、その場所の `profile.yaml` を確かめて直す)
   - NG なら指摘に従って YAML を直す (根拠の行番号の誤りは実ファイルで確かめて直す)。OK になるまで繰り返す
8. レビュー: **フレッシュなサブエージェント**に `abatlas-review-entry` を同じ入口 id で実行させ (作業定義に `analysis.models.review` があれば、そのモデルを指定して起動する)、`analysis/reviews/<file>` を `<abatlas> validate review analysis/reviews/<file> --result analysis/results/<file>` で確かめてから指摘を読む (読めない YAML なら、サブエージェントに直させる)
   - `severity: high` 以上の指摘は、必ず直す。medium と low は、直すか、直さない理由を結果の `notes` に書く
   - 直した指摘には、レビューのファイルの該当の指摘に `resolved: true` を書く (分析の側がレビューのファイルに書いてよいのは、この項目だけ。指摘の文や `where` は書き換えない。直した後に `where` の指す場所が動いても、指摘に従ってフレームを消して指す先が無くなっても、そのままでよい。`resolved: true` の指摘は、レビューの検査が、指す先の実在を見ない)
   - 直したら、7 (機械チェック) をやり直す
   - **もう一度レビューするのは、high を直したときだけ、1 回だけ**。フレッシュなサブエージェントに、同じ入口で実行させる (レビューのファイルは、新しい結果で置き換わる。1 回目に直さないと決めた指摘が、数から消えないよう、「前のレビューで直さなかった指摘」を、レビューの依頼に添える。レビューの側は、それを、新しいレビューのファイルに、直っていない指摘として引き継ぐ)。2 回目の指摘も同じ扱いで直すが、3 回目のレビューはしない。medium と low だけを直したときは、もう一度レビューしない
   - 最後に、結果の `analyzer.reviewed` を書く: `by` は、最後のレビューのファイルの `reviewer` の値。`at` は、同じファイルの `reviewed_at` の値。`findings_open` は、最後のレビューの指摘のうち、`resolved: true` でないものの数
9. 報告: フレーム数、I/O 件数、unknown の件数と理由の内訳、レビューで直した点

## 複数の入口をまとめて分析するとき

- 入口 1 件ごとに、フレッシュなサブエージェントにこの skill を実行させる。作業定義に `analysis.models.analyze` があれば、そのモデルを指定して起動する (書いてなければ、起動する側の既定で動く。多くの製品では、起動した側と同じモデルになり、入口が多いと費用がかさみ、利用の上限にも当たりやすい。書かれていないときは、始める前に、人に確かめる)
- 取りまとめる側は、結果の中身を読まない。サブエージェントの報告と、機械チェックの結果だけを見る
- **先に少ない件数 (2〜3 件) で試す**。迷った点と選んだ扱いを、分析リポジトリの `analysis-conventions.md` に書いてから、残りを流す。途中で決まりを足すと、先に分析した入口と書き方が揺れる。とくに、どの入口にも出る共通の段 (ログインの確認、持ち主の確認、接続先の設定、起動の仕組み) の、フレームの名前・確認の値・設定を書く段は、先に決めて書く (決めていないと、入口ごとに綴りと置き場が割れ、集計で同じ物が 2 つに分かれる)
- 取りまとめる側が `analysis-conventions.md` に決まりを足すときは、この skill とプロファイルの `context.md` の決まりと食い違わないかを確かめる (食い違う決まりを足すと、その後の結果がすべて、検査や見本のテストに落ちる)
- 入口 1 件を分析するサブエージェントは、木をさらに別のサブエージェントに分けない (分けた枝どうしで、同じ処理の置き場と綴りが割れる)。1 件が大きすぎるときは、止めずに書き切るか、決まりが許す所で打ち切り、分ける候補を報告する
- 同時に動かす数は、少なめにする (結果の綴りを、先に書かれた結果に合わせるため。利用の上限にも当たりにくい)

## 完了条件

- `analysis/results/<file>` が機械チェック OK
- `analysis/reviews/<file>` があり、`analyzer.reviewed.findings_open` が書かれている
- unknown の主張すべてに `reason` と、必要なら `note` (何を見て分からなかったか) がある

## 禁止

- 対象リポジトリのファイルを変える
- `analysis/entry-list.yaml` を変える
- 根拠の無い `fact`。読んでいないファイルを evidence に書く
- scope の外のファイルを evidence に書く (外なら `out_of_scope`)
