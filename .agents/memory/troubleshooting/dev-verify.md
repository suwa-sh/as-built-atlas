# 確かめるときの、はまり所 (このリポジトリの開発)

## 画面や集計を直したのに、確認用の画面が変わらない

- 適用対象: 画面 (abatlas/webapp/)、集計、meta、プロファイルの変更
- 症状: 直したはずの表示が、確認用の画面に出ない
- 原因: 確認用の画面は、配布物のイメージの中のファイルを配る。meta (呼び名、層の並び、対象の名前) と宣言は、集計のときに DuckDB に書く。画面を起動し直すだけでは、どちらも変わらない
- 検出: 画面のファイルだけの変更か、集計に関わる変更かを分ける
- 復旧: 画面だけなら、イメージの作り直しと起動し直し。集計に関わるなら、集計もやり直す (skill dev-webapp-verify の redeploy.sh --build)。このリポジトリの profiles/ や配布物を変えたなら、分析リポジトリの中のコピーも置き換える (redeploy.sh --upgrade)
- 再発防止: 変更の種類を、作業の最初に分けておく
- 最終確認日: 2026-11-15

## テストは通るのに、画面が壊れている

- 適用対象: abatlas/webapp/ の変更
- 症状: pytest は全部通るが、ブラウザで開くとエラーになる、または表示が崩れる
- 原因: テストは、ファイルの分け方と呼び名の書き方を見るだけで、JavaScript を実行しない
- 検出: ブラウザで開いて、コンソールのエラーを見る。node があれば `node --check <file>` で構文だけは確かめられる
- 復旧: skill dev-webapp-verify
- 再発防止: テストが通っても、実物で確かめるまで完了にしない
- 最終確認日: 2026-11-15

## 片方の見本でしか出ない表示を、出ない見本で確かめてしまう

- 適用対象: 画面の変更
- 症状: 「動いた」と報告したが、その表示が出る条件では確かめていない
- 原因: 見本によって、出る部品が違う。例: 確かめられていない線 (点線) と、function が 0 件の層は、バッチの見本にだけ出る。入口を包む入口と、未分析の入口は、画面を持つシステムの見本にだけ出る
- 検出: 変えた表示が、撮った画像に実際に写っているかを見る
- 復旧: 表示が出る見本で確かめる。出る見本が無ければ、確かめていないと報告する
- 再発防止: 確かめる前に、「どの見本で、どの状態なら出るか」を書き出す
- 最終確認日: 2026-11-15

## 確認用の見本を、試しに直したままにする

- 適用対象: プロファイルや作業定義を、確認用の分析リポジトリで試したとき
- 症状: README の画像や、後の確認が、既定とは違う状態で行われる
- 原因: 試した変更 (例: 層を 1 つ外したプロファイル) を戻していない
- 検出: 作業定義の profile.dir と、画面の層の数を見る
- 復旧: 配布物の既定のプロファイルに戻して、集計し直す
- 再発防止: 試す前に、戻し方を用意する。試した状態のままにするときは、報告に書く
- 最終確認日: 2026-11-15

## 配布イメージの両方の検査が、同じアーキテクチャを見てしまう

- 適用対象: リリースの OCI イメージをローカルで検査するとき
- 症状: amd64 と arm64 の両方が成功したように見えるが、Trivy の JSON の `Metadata.ImageConfig.architecture` が同じ
- 原因: 複数アーキテクチャの OCI ディレクトリを直接入力すると、`--platform` を変えても同じ manifest が選ばれることがある
- 検出と復旧: リリース手順と同じく skopeo でアーキテクチャを指定して別々のアーカイブに写し、`scripts/scan.py archive` の `--arch` で中身を照合する
- 最終確認日: 2026-11-22

公開後の週次検査を再現するときは、GHCR の `latest` が指す digest と、レポートの `org.opencontainers.image.revision` を控える。手元の HEAD を再ビルドすると OS の更新が入るため、公開イメージに残る指摘を再現できないことがある。

Buildx の digest と OCI レイアウトを照合するときは、`skopeo inspect --raw oci:<ディレクトリ>` の出力をファイルに保存し、`skopeo manifest-digest` に渡す。`index.json` はイメージの manifest を指すため、そのファイル自体の SHA-256 はビルド結果と異なる場合がある。

## ローカルと CI で複雑度が異なるとき

同じ関数でも Qlty の版によって計測値が変わる。手元でだけ上限超過が出たら、`qlty --version` と `mise exec -- qlty --version` を比較し、`mise exec -- scripts/check main lint` で CI と同じ版を使って再現する。

## コミットフックを検証するとき

- 部分ステージは「ステージにだけ指摘がある場合」と「作業ツリーにだけ指摘がある場合」の両方を試す。`git commit --only -- <path>` では Git が別の index を渡すため、実際のコミットでも確認する。
- 浅い clone では `git clone --shared` でステージ済みの未コミットオブジェクトを読めないことがある。一時チェックアウトで `git read-tree` が失敗したら、元の object database を参照しているか調べる。

- 文書フックは、参照形式の画像の削除をステージし、作業ツリーには同じ画像を残して試す。修正前の文書や作業ツリーを調べていると、この削除を見逃す。

## 差分分析の見本で固定コミットを列挙する

ことり書店の対象と分析資産を別々の一時 Git リポジトリにし、見本の対象コミットを実際の対象 SHA に合わせてから基準版を保存する。対象を読み取り専用でマウントし、配布イメージの `impact` で入口数まで確認する。一時 clone で `read-tree` すると index だけが埋まる。列挙には作業ツリーへの展開も必要。
