# 0016: 別の入口に分ける候補は、プロファイルが決めた層の処理だけを出す

- 日付: 2026-11-19
- 状態: 採用

## 背景

[0014](0014-shared-parts-as-entries.md) で、集計表「別の入口に分ける候補」を足した。3 件以上の入口が通り、下に 10 以上の段を持つ処理を、繰り返されている段の多い順に出す。

umami で部品を 1 つ分けた後、表の上位は、分けられない処理になった。

| 順 | 処理 | 層 | 分けられるか |
|---|---|---|---|
| 1 | サイトを見られるかの確認 | サーバー側の関数 | 分けられない |
| 2 | 対象を読む共通の関数 | サーバー側の関数 | 分けられない |
| 3 | サイトの区画を見られるかの確認 | サーバー側の関数 | 分けられない |
| 4 以降 | セッションの小窓、絞り込みのボタンなど | 画面のコンポーネント | 分けられる |

98 件のうち 33 件が、受け口とサーバー側の関数だった。0014 は「対象は、画面が描くコンポーネントだけ」と決めていたが、表は層を見ていなかったので、表の説明に「出ても分けない」と書いて済ませていた。

## 決めたこと

| 決めたこと | 中身 |
|---|---|
| 分けられる層を、プロファイルが宣言する | `profile.yaml` の、入口の層に `split_from` (層の id の並び)。「この層の入口は、どの層のフレームを分けたものか」を書く |
| 候補の表は、宣言された層の処理だけを出す | 取り込みが、フレームに印 (`splittable`) を付け、集計が絞る |
| 宣言の無いプロファイルでは、候補は出ない | 部品を別の入口に分ける決まりを持たないプロファイル (API、バッチなど) |
| 宣言するのは、部品の決まりを持つ 4 つ | `ui-nextjs`、`ui-vue-router`、`ui-nuxt`、`ui-sveltekit` の `part` に `split_from: [component]` |

## 考えた案

| 案 | 採らなかった理由 |
|---|---|
| 層の区分 (`tier`) が、入口の層と同じ層を、分けられると見なす | `ui-vue-router` は、状態の置き場と API を包む関数も同じ区分で、分けられない層が混ざる。`tier` は図のための項目で、分析や集計に使わないと決めている |
| 集計の SQL に、層の id (`component`) を直接書く | 集計は、どのプロファイルでも同じものを使う。プロファイルごとの知識を、集計に持たせない |
| 表は変えず、分けられない行に印を付ける | 上から順に見る表なので、分けられない行が上に並ぶと、使いにくいまま |
| 分けられない処理を、別の表に出す | 使い道 (何を直せるか) が無い。要るときは、分析の状態のほかの表で見られる |

## 影響

- プロファイルの形式に、任意の項目が 1 つ増える。書いていないプロファイルも、そのまま読める。
- プロファイルの版は、上げない。集計の出し方だけが変わり、分析の判断は変わらない。
- 手元の分析リポジトリは、プロファイルを新しくして集計し直すと、候補の表が絞られる。独自のプロファイルで候補を出したいときは、入口の層に `split_from` を書く。
