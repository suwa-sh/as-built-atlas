# 0013: 設定で選ばれて描かれる部品を、別の入口に分けられるようにする

- 状態: 採用
- 関連: [0011](0011-agent-enumerates-entries.md)、[0012](0012-result-aspects.md)

## 背景

画面が、保存された設定 (データベースに保存した画面の構成など) で、描く部品を決める作りがあります。コードには、名前から部品を引く登録表があり、どの部品が描かれるかは、実行時の値で決まります。

これまでの決まり (候補が有限で全部読めるなら、それぞれを処理の段にする) で、実在の公開ソフトのボードの画面を分析したところ、次のことが起きました。

| 起きたこと | 中身 |
|---|---|
| 1 件の分析が、とても大きくなった | 登録表の 17 種類の部品をすべて辿り、処理の段が 313 になった |
| 同じ部品を、何度も分析した | 同じ登録表を使う画面が複数あり、画面ごとに、同じ部品の経路を書いた |
| 部品ごとの見通しが無い | 「この部品が、どの API を呼ぶか」が、大きな木の中に埋もれた |

## 決めたこと

| 決めたこと | 中身 |
|---|---|
| 部品を、部品ごとに別の入口に分けられる | プロファイル `ui-nextjs` に、入口の層 `part` を足した。登録表の項目 1 つが、入口 1 件。エージェントが、根拠を付けて入口の一覧に足す |
| 分けるかは、入口の一覧で決まる | 部品が入口の一覧に入っていれば、画面は、登録表を引く段で止める。入っていなければ、これまでどおり、画面の中で辿る |
| 画面と部品は、つながりで結ぶ | つながりの種類に `embed` (この入口の中に描く、別の入口にした部品) を足した。登録表を引く段に書く |
| 行き先の入口が分かっているつながりを持つ段は、終端にできる | `embed` と `trigger` で、行き先の入口 (`entry_id`) が書いてあるもの。続きは、行き先の入口の結果にあるため。`embed` は、`entry_id` を必須にし、機械チェックと集計が、入口の一覧と照合する (行き先を書かずに、または無い入口を書いて、辿るのを止める抜け道にしない) |
| プロファイルの版は上げない | 入口の一覧で選んだときだけ効く決まりで、これまでの結果 (部品を入口にしていない) と矛盾しないため |

## 理由

- 入口を分ける仕組み (画面と枠、枠と共通の部品) は既にあり、同じ考え方で扱える
- 分けるかを入口の一覧で決めれば、人が承認のときに選べる。小さな登録表 (候補が 2 つ以下) まで分ける必要は無い
- つながりにしておけば、「この部品を描く画面はどれか」を、入口どうしのつながりの表で引ける

## 影響

- 部品の入口を足した・外したときは、その登録表を引く画面を分析し直す必要がある。これは、プロファイルの版の比較では見つからない (入口を見つける skill の報告に書く決まりにした)
- 部品の入口からは、「どの画面も、その値を渡さない」ことを決められない。描く側が渡す値で動きが変わる所は、候補をすべて辿って、条件つきにする
- `ui-vue-router` には、まだ入れていない (枠が描く共通の部品を分ける決まりは、既にある)
