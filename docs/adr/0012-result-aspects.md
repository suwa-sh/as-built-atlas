# 0012: 分析結果に観点をまとめて足し、区分は辞書に持つ

- 状態: 採用
- 関連: [0009](0009-field-names-match-labels.md)、[0010](0010-migrate-command.md)

## 背景

分析結果が答えられる問いは、「入口から何が呼ばれ、どのデータを読み書きするか」まででした。次の問いには、答えられませんでした。

| 問い | 無かったもの |
|---|---|
| どの列を読み書きするか。状態の値を変えるのはどこか | 読み書きは、テーブルの単位まで。列は、自由に書ける `detail` の文の中 |
| その処理は、いつも動くか。失敗したら何が動くか | 呼び出しの木はあるが、枝が「いつも / 条件つき / 失敗のとき」のどれかの区別が無い |
| ほかの入口へ、どうつながるか | 無い |
| 誰が使えるか (権限の確認) | 無い |
| どの設定で動きが変わるか | パラメータの文の中 |
| 業務のルールは、どこにあるか | 概要の文の中 |
| テストはあるか | 無い |
| 個人情報は、どこを通るか | 無い |

これらを足すと、分析の判断が変わるので、分析の skill の版が上がり、これまでの結果がすべて再分析の対象になります。1 つずつ足すと、利用者は、足すたびに分析し直すことになります。

## 決定

| 決めたこと | 内容 |
|---|---|
| まとめて 1 回で足す | 観点を 1 つの版 (分析の skill 0.4.0) に入れる。再分析は 1 回で済む |
| 足す項目は、すべて任意 | 形式の版は上げない。前の結果は、形式の上ではそのまま読める。前の結果かどうかは、分析の skill の版で見分ける (集計の入力の `aspects_analyzed`) |
| 観点は選ばせない | 列、呼び出しの条件、つながり、権限の確認、設定、業務のルールは、いつも分析する。選べるのは、テストとの対応だけ (作業定義の `analysis.tests`) |
| 失敗したときの動きは、呼び出しの条件で表す | `call.when` に `on_failure` を持つ。まとめて取り消される範囲や、やり直しの安全さは、持たない |
| 区分 (個人情報など) は、分析結果に書かない | データの辞書 (`analysis/data-dictionary.yaml`) に、列ごとに 1 回だけ書く。エージェントが案を書き、人が承認する |
| 項目名は、用語集と意味が重ならない語にする | 設定の種類とテストの種類は `kind` (`source` は定義の場所、`level` は階層の段の意味で、既に使っている) |

## 選ばなかった案

| 案 | 選ばなかった理由 |
|---|---|
| 観点を、分析リポジトリごとに選べるようにする | 「分析していない」と「無かった」を、結果ごとに覚える項目が要る。費用が問題になるのは、範囲にテストが要る、テストとの対応だけだった |
| 区分を、読み書きのたびに分析結果へ書く | 同じ列の区分が、入口ごとにぶれる。直すには、分析し直しが要る。区分は、人が決めたい |
| 入口ごとに、認証の要否を 1 つの主張で書く | 画面は、包む側の入口 (枠) が認証を確かめることが多い。包まれる側の結果だけでは、決められない。集計で、包む入口の確認と合わせて出す |
| つながりの行き先を、入口の id だけで書く | 分析のときに、行き先が一覧のどれかを決められないことがある。コードに書いてあるとおりの行き先を必ず書き、突き合わせは集計が行う |
| 失敗のときの書き込みの範囲 (トランザクション) も書く | 読み取りが難しく、費用が増える。まず、失敗のときに何が動くかを出す |

## 影響

- 分析の skill の版が 0.4.0 になり、0.3.0 までの結果は再分析の対象になる。再分析するまで、足した観点の集計表は、その入口について空になる。
- 分析 1 件の費用が増える。
- 個人情報の流れは、「個人情報の列を使う入口が、外部も呼ぶ」という粗い形で出る。その値が実際に外へ送られるかは、追っていない。
- 足した集計表は、分析の状況の区分に置いた。入口のページでは、入口ごとに絞ったタブとして出る。専用のページは、まだ無い。
