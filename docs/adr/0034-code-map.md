# 0034. 入口の列挙を対象コミットの定義ファイルと照合する

- 状態: 採用
- 記録した日: 2026-11-23

## 背景

入口一覧を同じ抽出器で作り直しても、探索先の設定から漏れたディレクトリは両方の一覧から消える。分析後の未到達ファイルには、入口を持たない共通処理も含まれる。

reverse-spec-flow は最初にモジュール・入口・外部境界を並べ、別経路で数えた要素と照合する。ここから、対象の集合を先に決めて漏れをパス単位で示す考え方を取り入れた。[コードグラフのひな形](https://github.com/aws-samples/sample-reverse-spec-flow/blob/caa0a9d147b79d7bb4432552554611c24afe8be1/templates/code-graph.md.template)・[列挙の照合](https://github.com/aws-samples/sample-reverse-spec-flow/blob/caa0a9d147b79d7bb4432552554611c24afe8be1/templates/gates.sh#L2801-L2814)

## 決定

対象コミットの通常ファイルからコードマップを生成する。定義ファイルの置き場に規約がある対象では、分析者が作業定義にその範囲を書く。作業案の作成と確定時に、各ファイルから入口が少なくとも一つ列挙されたことを検査する。

| 検討した方法 | 判断の理由 |
|---|---|
| 入口の総数を比べる | 一方で定義が漏れ、別の場所で重複すると件数が一致する |
| 全ファイルに入口との対応を要求する | 共通処理や文書まで入口として扱うことになる |
| 呼び出しや外部境界も先に手で一覧にする | 入口別の分析結果と二重に保守することになる。これらの関係は既存の根拠付き分析で記録できる |

## 結果

抽出器の探索先を狭めても、作業定義で指定したファイルの取りこぼしが承認前に分かる。規則の及ぶ範囲と、同じファイル内に複数ある登録の網羅性は分析者が確かめる。[利用手順](../architecture/impact.md)
