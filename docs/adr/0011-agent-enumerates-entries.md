# 0011. 入口の列挙は、道具を土台にして、エージェントが仕上げる

- 状態: 採用
- 記録した日: 2026-11-16

## 背景

これまでは、入口を列挙するのは道具 (抽出器) だけだった。エージェントは、抽出器の設定を書くだけで、入口を手で足すことは禁じていた。同じ設定から、いつも同じ一覧を出すためである。

対象の種類を増やすと、この決まりでは入口が漏れる。コードの中でルーティングを定義する画面を、公開されている実物 (Kestra の画面の定義) で試した。

| 定義の書き方 | 道具で読めるか |
|---|---|
| その場に書いた定義 (41 件) | 読める |
| 別のファイルで定義して、名前で並べたもの (2 件) | その場では、中身が分からない |
| 関数が作る定義 | 静的には、列挙できない |

道具が読めない言語 (Vue の単一ファイルなど) もある。道具が取れた分だけを一覧にすると、取れなかった入口は、分析されないまま気づかれない。

## 決定

- 入口を列挙する主体は、エージェント (入口を見つける skill) にする。道具は、その土台である。
- 道具が成功しても失敗しても、skill は一覧を仕上げる。道具で取れない入口は、エージェントがコードを読んで足す。

| 決めたこと | 内容 |
|---|---|
| 構文を読む道具 | コア同梱の抽出器 `abatlas-extract ast` を足す。構文の一致には ast-grep を使う。読めなかった場所を探す規則を書くと、その場所を知らせる |
| その場で調べるコマンド | `abatlas code-search` を足す。規則に一致した場所を出すだけで、一覧は変えない |
| エージェントが足す入口の置き場 | コア同梱の抽出器 `abatlas-extract listed` の設定 (`params.entries`) に書く。入口の一覧の `entries[]` には、直接書かない |
| 根拠 | 足す入口には、根拠 (ファイルと行) と、理由を必ず書く。`listed` が、ファイルの実在と行を確かめる |
| 印 | `listed` が出した候補には、`attributes.listed_by: agent` と `attributes.reason` が付く。人は、承認のときに見分けられる |
| 道具の失敗 | 規則の誤りや、読めない言語は、理由を出して止まる。skill は、その抽出器を設定から外し、読んで足す |
| 承認 | 道具が出した入口も、エージェントが足した入口も、人が承認する。承認の後に、同じ id の指す先 (階層パス、層、定義のファイル) が変わったら、列挙が `candidate` に戻す。行と、理由の文だけの違いでは戻さない (理由の文は、エージェントが書き直すたびに言い回しが変わるため) |
| id の重なり | 2 つの抽出器が、同じ id を、指す先の違う入口として出したら、列挙は止まる |

`entries[]` に直接書かせない理由は、列挙をやり直すと消えるためである。設定に書けば、列挙のたびに同じ候補が出て、承認の状態も引き継がれる。

## 捨てた案

| 案 | 捨てた理由 |
|---|---|
| 道具だけで列挙する (これまでの決まり) | 静的に読めない定義が漏れる。漏れに気づく手段も無い |
| エージェントが、入口の一覧の `entries[]` に直接書く | 列挙のやり直しで消える。道具の結果と混ざって、どちらが出したか分からなくなる |
| 足した入口を、別のファイルに置く | 抽出器の契約 (引数は、対象の場所・層・設定) を変えることになる。設定の中に書けば、契約も形式も変えずに済む |
| 道具が失敗しても、列挙を続ける | 壊れた設定で列挙が進み、前に承認した入口が一覧から消える |
| tree-sitter と、言語ごとの文法を直接使う | 言語ごとに依存が増える。文法の詰め合わせは、実行のときに文法を取りに行く。ast-grep は、1 つの依存に 23 言語を同梱し、ネットワークなしで動く |

## 結果

- 同じ設定から同じ一覧が出る、という性質は残る。エージェントが足した入口も、設定に書かれているためである。変わるのは、設定を書くときに、エージェントの判断が入る範囲である。
- エージェントが足した入口は、道具が出した入口より誤りやすい。人は、印の付いた入口を、理由と根拠を読んで承認する。
