# 0017: 見本を、プロファイルごとに 1 つ持つ

- 日付: 2026-11-19
- 状態: 採用

## 背景

見本は 2 つだけだった。架空のバッチ (ことり書店、`batch-kestra`) と、実在の公開ソフト umami の画面 (`ui-nextjs`)。決まりは「umami だけが例外。ほかの実在のソフトの分析結果は、入れない」だった。

プロファイルは 11 に増えた。残りの 9 つは、分析結果の実例がリポジトリに無かった。

| 困ること | 中身 |
|---|---|
| 書き方が分からない | プロファイルの説明は決まりの文だけで、「その型のシステムを分析すると、結果がどうなるか」を見られない |
| プロファイルを直したときに、確かめる相手が無い | 形式やプロファイルを変えても、9 つのプロファイルでは、集計が通るかをテストで確かめられない |
| 手元にだけある | プロファイルを作るときに試した分析結果は、作った人の手元にしか無い |

## 決めたこと

| 決めたこと | 中身 |
|---|---|
| 見本は、プロファイルごとに 1 つ | どのプロファイルにも 1 つ。同じプロファイルに 2 つ目を足さない |
| 対象は、公開されているソフト | 公開されていない対象の分析結果は、これまでどおり入れない |
| 入れるのは、分析リポジトリの資産だけ | 作業定義、入口の一覧、分析結果、レビュー。対象のコードは入れない (umami と同じ) |
| 件数は、書き方が分かる数でよい | 承認して分析した入口が 3 件以上。全部の入口を分析しなくてよい (残りは、候補のまま一覧に残る) |
| 対象のライセンスは問わず、README に書く | 見本ごとの README に、対象、コミット、ライセンスを書く |
| 写すのは、スクリプトで | `examples/generator/import_atlas.py` が、資産を写し、手元の場所 (`clone_path`) を `../<対象の clone の名前>` に置き換える |
| テストが、1 対 1 を確かめる | `tests/test_examples_profiles.py`。見本の無いプロファイルも、2 つ目の見本も、テストが落ちる |

## 考えた案

| 案 | 採らなかった理由 |
|---|---|
| 自分のソフトと架空の題材だけにする | 画面の 5 つのプロファイルなどで、題材を新しく作ることになる。作った題材は、実在のソフトより単純になり、見本として弱い |
| 全部の入口を分析する | 合わせて約 300 件の分析が要る。プロファイルの書き方を見せる目的には、3 件で足りる |
| コピーレフトや独自のライセンスの対象を避ける | 見本は対象のコードを写さない (パスと行番号、要約、データの名前だけ)。対象を選び直すと、分析し直しが要る |
| API の見本を、ほかの公開ソフトにする | as-built-atlas 自身の API なら、対象が同じリポジトリの履歴にあり、ライセンスの心配が無い |

## 影響

- 見本は 11 個になる。対象は、[../architecture/examples.md](../architecture/examples.md) の表のとおり。
- プロファイルを足すときは、見本も足す (テストが求める)。プロファイルの版を上げたら、その見本を分析し直す (テストは、今の版で分析した結果だけを通す)。
- ライセンスの判断 (コードを写さないので、対象のライセンスの条件は及ばない) は、法務の確認を経ていない。対象の開発元から求めがあれば、その見本を外して、別の対象で作り直す。
- umami の見本は、全部の入口を分析した見本として残す (件数の決まりは「3 件以上」なので、そのまま当てはまる)。
