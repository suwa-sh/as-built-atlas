# 0031. 開発時・コミット時・CI で機械チェックの対象を選ぶ

- 状態: 採用
- 記録した日: 2026-11-22

以前の CI は pytest と製品別設定の再生成結果を検査していた。配布イメージにある OS や実行ファイルの依存は、Python のテストが通っても更新漏れに気付けなかった。

機械チェックの入口を一つにする。整形と静的解析のツールは Qlty の自動選定を使う。コミットフックはステージした秘密を検出し、同じステージ内容の整形と lint を検査する。部分ステージでもコミット対象だけを読むため、一時チェックアウトで検査する。Markdown には Qlty の markdownlint を使い、整形と見出しなどの検査を同じ規則に揃える。リンク先だけの削除でも未変更の文書が壊れるため、文書テストは全量をフックでも実行する。CI はロックファイルと実際の配布イメージまで検査する。配布タグを付ける前に、プラットフォームごとの内容を検査する。

パッケージの書き込み権限は公開ジョブに限る。ビルドジョブが両アーキテクチャを含む OCI イメージを artifact として保存し、検査ジョブと公開ジョブは同じ ID から別々に取得する。公開前に Buildx の digest と照合する。これで依存のインストールと検査は GHCR に書き込めない環境で実行される。

修正版が公開された依存は深刻度を問わず更新する。推移的な依存に限り、直接依存の公開版が修正版を取り込めない根拠を記録して例外を認める。手順と失効条件は[機械チェックのルール](../rules/checks.md)にある。

呼び出し側は開発、コミット、PR、main の場面を一つ選ぶ。場面ごとに検査範囲が決まるため、範囲を別の引数で指定すると CI の設定を取り違えやすい。開発時と PR は変更差分を、main への push は全量を検査する。テスト・生成物・依存関係は差分から影響先を特定しきれないため、両方で全量を検査する。新しい脆弱性の発表はコードの変更と独立しているため、週次の Actions で公開中のイメージとロックファイルを再検査する。

循環的複雑度は関数単位の上限を 10 とする。独立した実行経路が多い関数を見直すため、NIST SP 500-235 の目安を採用した。lint の上限判定と手元での一覧に同じ Qlty の計測値を使う。どの業務ルールを分けるかは、その責務とテストを読んで決める。[NIST SP 500-235](https://doi.org/10.6028/NIST.SP.500-235)

dbt の SQL は SQLFluff の DuckDB 方言でソースを検査し、プロファイルや repo 独自モデルとの組み合わせは既存の dbt ビルドで試す。モデルの見直しには、コンパイル後の JOIN・CTE の件数と dbt が解決した直接依存数を使う。マクロ内の分岐や SQL の構造は Python・JavaScript の関数と性質が違うため、モデル別の一覧には関数の上限値を適用しない。

Web 画面と公開サイトは Prettier と Biome でソースを検査し、pytest から同じ Chromium で操作を確かめる。JSON・YAML の整形と重複キーの検出も通常のモードに含める。ブラウザの準備と実行は開発と CI のテストに含め、コミットフックはステージ内容の静的検査と文書テストに絞る。
