# 0014: 多くの入口が描く、大きな部品を、別の入口に分けられるようにする

- 日付: 2026-11-19
- 状態: 採用

## 背景

[0013](0013-parts-as-entries.md) で、保存された設定で選ばれて描かれる部品を、別の入口に分けられるようにした。実物で分析を重ねると、設定で選ばれるのではなく、**多くの画面が、いつも自分で描く大きな部品**でも、同じことが起きていた。

| 題材 | 起きたこと |
|---|---|
| umami (入口 82 件、処理の段 約 6,000) | サイトの画面の上の操作の部品が、21 の入口に 108 段ずつ書かれていた。繰り返しは約 1,100 段 |
| Papermark | 文書の一覧の画面 1 件が 146 段になり、分析に約 140 万トークンかかった。分析したエージェントは、枝を別のエージェントに分け、途中で打ち切った所がある |

同じ木を入口の数だけ分析するので、費用が増え、入口ごとに書き方が割れる。

## 決めたこと

| 決めたこと | 中身 |
|---|---|
| 多くの入口が描く、大きな部品を、別の入口 (`part`) にできる | 階層は `/(part)/_shared/<コンポーネントの名前>`。描く側は、部品を描く段で止めて、つながり (`embed`) で指す。0013 と同じ仕組み |
| 候補は、集計が出す | 集計表「別の入口に分ける候補」(`mart_split_candidates`)。3 件以上の入口が通り、下に 10 以上の段を持つ処理を、繰り返されている段の多い順に出す |
| 分けるかは、人が決める | 入口の一覧に足して、承認する。足したら、その部品を描く入口を分析し直す |
| 対象は、画面が描くコンポーネントだけ | サーバー側の関数 (受け口、問い合わせ、権限の確認) は、分けない |

## 考えた案

| 案 | 採らなかった理由 |
|---|---|
| 最初の発見のときに、エージェントが、大きな部品を見つけて分ける | 分析する前は、どの部品が大きいかが分からない。決定論で出せる数 (集計) を、判断の材料にする |
| 条件を満たす部品を、自動で入口にする | 入口の数が大きく変わる (umami で候補は 105 件)。大きな部品の中の部品も候補に出るので、外側から選ぶ判断が要る |
| サーバー側の共通の関数 (ログインの確認など) も分ける | 部品ではなく、どの入口の経路にも要る段。分けると、入口ごとの「権限の確認」が、経路から消える |

## 影響

- プロファイルの版は、上げない。入口の一覧に部品を足したときだけ効く決まりで、これまでの結果と矛盾しない (0013 と同じ)。
- 入口を足すのは、分析が進んだ後になる。入口を見つける手順に、「分析が進んだ後に、入口を見直す」を足した。
- 同じ入口の中で、同じ処理をもう一度書いた段の読み書きは、集計で 2 回数えないようにした (`stg_io` の `is_repeat`)。これは、部品を分けるかどうかに関係なく効く。
