# `ui-nextjs` の決まり

[← プロファイルの仕様へ](../profiles.md)

## 入口の id と階層

| 対象 | 決まり |
|---|---|
| 画面 (page) | URL の区切りが段。`[section+, page]` |
| 枠 (layout) | 階層は `/(layout)/<置き場のフォルダ>`。id は `layout_l` で始まる |
| 登録表から選ばれて描かれる部品 (part) | 階層は `/(part)/<登録表の名前>/<選ぶときの名前>`。id は `part_p` で始まる。エージェントが、入口の一覧に足したときだけ入口になる |
| URL に出ない入れ物 `(group)` | 落とす |
| `_folder` の下 | 拾わない |
| id | 記号を除き、段の種類を印で区別する (`[id]` → `id_d`、`@modal` → `modal_s`、app 直下 → `root_r`)。名前の中の `_` は重ねるので、同じ名前の静的な段と同居できる |
| 小窓版 (並行ルート + 割り込みルート) | 階層は、割り込み先の URL ではなく、置き場を表す |
| Pages Router の画面 | 拡張子を除いたファイル名が最後の段。ファイル名の `index` は段にしない (`pages/index.tsx` → `/(root)`)。段の印は App Router と同じなので、同じ URL は同じ id (移行しても変わらない) |
| Pages Router の `_app` | 階層は `/(layout)/_app`、id は `layout_l.app_a`。`pages` の下の画面だけを包む |
| middleware | 階層は `/(layout)/_middleware`、id は `layout_l.middleware_a`。データか外部への送信に至るときだけ入口にする。包むのは、middleware の置き場のフォルダの下にある入口 (範囲の直下に置けば、すべての入口。`matcher` で絞っていても)。`src/middleware.ts` と、`src` の外の `pages/` が同居する配置では、`pages/` の画面を包む関係が付かない (枠の要約に書く) |
| 多くの入口が自分で描く、大きな部品 (共有の部品) | 階層は `/(part)/_shared/<コンポーネントの名前>`、id は `part_p.shared_a.<名前>`。候補は、数件を分析した後に、集計表 (別の入口に分ける候補) から選び、人が承認で決める。描く側は、部品を描く段で止めて、つながり (`embed`) で指す (経緯は ADR 0014。`ui-vue-router`、`ui-nuxt`、`ui-sveltekit` も同じ)。候補の表に出る層は、`profile.yaml` の `part` の `split_from` で決める (`component`。経緯は ADR 0016) |
| 多くの page が自分で描く共通の枠 (`getLayout`、`<AppLayout>`) | 3 つ以上の page が描き、データに届くものを、エージェントが足す。階層は `/(layout)/_shared/<名前>`、id は `layout_l.shared_a.<名前>`。page は枠を辿らず、つながり (`embed`) で指す |

## 既定では入口にならないもの

| もの | 扱い |
|---|---|
| API の受け口 (`route` ファイル) | 入口にしない。画面から辿った途中の段として現れる。画面を通らない受け口 (外部向けの API、計測の受信) は、分析の対象にならない |
| `template`、`loading`、`error`、`not-found`、`default` のファイル | 既定の抽出器では拾わない。画面も枠もこれらを辿らないので、入口を発見するときに、有無と中身を確かめる |
| Pages Router の API の受け口 (`pages/api`) | 入口にしない。`route` ファイルと同じく、画面から辿った途中の段 (HTTP メソッドの分岐ごと) |
| `_document`、`_error`、`404`、`500` | 既定の抽出器では拾わない。入口を発見するときに中身を確かめ、データに届くときだけ足す |

枠の動きが、画面や URL によって変わることがあります。その差は、枠の要約に文で書くだけで、表にはなりません。

## バッチと違う所

どちらも `context.md` に書いてあります。

**1. 画面の部品から API の受け口への入り方が、2 通りある。**

| 入り方 | 辿り方 | 根拠 |
|---|---|---|
| URL (Route Handler) | ブラウザ側のフックが呼ぶ URL の文字列 (例 ``get(`/websites/${websiteId}/stats`)``) を、その形に当たる `route` ファイルの、HTTP メソッドの関数に対応付ける | URL の行。形が決まらなければ `unknown` + `dynamic_dispatch` |
| 関数の参照 (`'use server'` の Server Function) | URL を通らないので、import や props を辿って、関数の定義へ行く | — |
| サーバー側のデータ取得の関数 (Pages Router の `getServerSideProps` / `getStaticProps` / `getInitialProps`) | page と別の段 (`api_route`) にする。Next.js が名前で呼ぶので、根拠は定義の行 | — |

同じ `route` ファイルの GET と POST は、別の段にします。突き合わせ (`evaluate`) は、ファイル単位で照合します (メソッドの取り違えは、読み書きの照合に現れます)。

**2. 接続先 (host / database) が環境変数で決まるときは、その段を書かず、それだけを理由に `unknown` にしない。**

| プロファイル | 接続先が環境変数のとき | 理由 |
|---|---|---|
| `ui-nextjs` | 接続先の段を書かない。テーブルやキーがコードから読めれば `fact` | 接続先は実行環境の設定で決まり、どの画面でも同じになる |
| `batch-kestra` | 読み書き全体を `unknown` + `not_traceable_in_repo` にする | プロファイルごとの決まり。形式は同じ |

接続先がコードに直接書いてあるときは、その段も書きます。

## 分析者によって書き方が割れた所

umami での試し分析で、3 つありました。`context.md` で、次のように決めています。

| 割れた所 | 決まり | 理由 |
|---|---|---|
| `external` の段の場所 | ライブラリのメソッドを実際に呼んでいる行を `source` にする (クライアントを作るだけの共通ファイルにしない) | 突き合わせが、段を「層とファイル」で照合する。場所の取り方が割れると、中身が同じでも食い違う |
| 全画面共通の枠 (祖先の layout と、そこから描かれる部品) | 枠を 1 件の入口 (`layout`) として、1 回だけ分析する。画面は枠を辿らず、枠は `children` の中身を辿らない | 画面を開いただけで起きる書き込みや外部への送信を表に出しつつ、同じ通り道を画面の数だけ繰り返さない。はじめは「画面ごとに終端まで辿る」と決めたが、1 画面の分析の 4〜5 割が枠になった |
| 保存された設定で、描く部品が決まる画面 (名前から部品を引く登録表) | 部品を、部品ごとに別の入口 (`part`) に分けられる。分けるかは、入口の一覧で決まる (データに届く部品が 3 つ以上なら分ける)。画面は、登録表を引く段で止め、部品へのつながり (`embed`) を書く | 候補をすべて 1 つの画面で辿ると、処理の段が 300 を超え、同じ部品を画面の数だけ繰り返した (経緯は ADR 0013) |
| 同じ処理が、複数の呼び出し元から呼ばれるとき | 1 つの入口の中では、入口から、コードに書いてある順に深さ優先で辿って、最初にその処理に着いた呼び出し元の下に、1 回だけ書く (はじめは「呼び出しの行のファイルのパスの辞書順」で決めていたが、実際に動く順と逆の木になることがあった)。他の呼び出し元は、`summary` で「同じ経路」と指す。例外は 2 つ: そうすると呼び出し元が終端になって機械チェックに落ちるとき、同じ処理の中の分かれ道が、呼び出し元によって閉じたり開いたりするとき (開いている呼び出し元の下に、もう一度書く。経緯は ADR 0015) | 何度も書くと、読み書きの件数が水増しされ、分析の費用も増える |
