# `api` の決まり

[← プロファイルの仕様へ](../profiles.md)

| 決まり | 内容 | 理由 |
|---|---|---|
| 層は、役割で分ける | operation (入口) → handler (操作を受け持つ関数と、操作に掛かる middleware) → logic → adapter → external | `cli` と同じ。言語や、フォルダの分け方は、対象ごとに違う |
| 入口は、呼び出す側から見た操作 1 つ | HTTP なら、URL とメソッドの組。階層は、URL の区切りの後ろに、メソッドを置く (`GET /users/{id}` → `/users/{id}/get`) | 同じ URL でも、メソッドごとに処理が違う。URL の区切りを段にすると、資源ごとにまとまる |
| 入口の出どころは、定義ファイル。コードの登録と突き合わせる | 定義ファイル (OpenAPI など) があれば、そこから列挙する。コードにあって定義に無い操作は、エージェントが足す。定義にあってコードに無い操作は、入口のまま残す | 定義ファイルは、呼び出す側との約束。実装との食い違いも、分析の結果として見える |
| 入口のフレームは、定義ファイルの操作。そこから、コードの登録の行を根拠に、受け口の関数へつなぐ | 当たる登録が見つからなければ、受け口のフレームを作らず、不明 (リポジトリの中で辿れない) にする | 定義とコードは、関数の呼び出しではつながらない。つないだ根拠を残す |
| 定義とコードが食い違うときは、コードを正として書く | 食い違いは、入口のフレームのメモに書く | 分析結果は、作られたとおりの姿を表す |
| 操作に掛かる middleware は、その操作の経路に書く | 権限の確認・読み書き・外部の呼び出しをするものだけ。先は、読み書きを持つ最初の段まで | 権限の確認を、入口ごとに見えるようにする。同じ経路を、操作の数だけ、終端まで繰り返さない |
| HTML を返す route も、データを読み書きするなら入口 | サーバー側で画面を作る webapp (route → controller → model) も、このプロファイルで扱う。入口にしないのは、中身が決まっているものを返すだけの route (静的なファイル、ブラウザ側で動く画面の殻) | 入口から、受け口・処理・データへ辿る流れが、API と同じ。応答の形は、分析の単位を変えない |
| コードにだけある別名の登録は、足さない | 定義ファイルにある操作は、すべて入口のまま。コードにだけある登録が、既にある入口と同じ関数の別名なら、足さずに、理由に書く。コードにだけある登録どうしが同じ関数なら、利用者が使う形を 1 つ残す (登録の順では決めない)。ページ送りや、形式だけ違う path は、別名 | 定義ファイルは、呼び出す側との約束なので、欠かさない。同じ処理を、2 回数えない。実物 (Rails) では、利用者が見る URL の方が、後に登録されていた |
| HTTP の path でない操作は、先頭に、かっこで囲んだ種類の段を置く | MCP は `/(mcp)/<tools など>/<名前>`、gRPC は `/(grpc)/<package>.<Service>/<Method>`、GraphQL は `/(graphql)/<query など>/<field>` | HTTP の操作と同じリポジトリにあっても、木が分かれる。かっこの段は、作った段 (ほかのプロファイルの `(root)`、`(layout)` と同じ書き方) |
| gRPC の入口は、サーバーに登録した service の method | 生成したコードや定義にあっても、登録していない service (呼ぶ側のスタブ) は入口にしない。定義 (`.proto`) が範囲の外なら、範囲の中の生成したコードか、登録の行を根拠にする | 実物では、生成したコードに、10 個の service の 15 個の method があり、登録しているのは 1 つだけだった |
| 入口を見つける抽出器の例を、説明書きに載せる | 定義ファイルが無い作り (FastAPI、echo、Rails、MCP の SDK、gRPC の生成したコード) の、実物で動いた設定。id の規則は、定義ファイルの抽出器のものを写す | 例が無いと、分析者ごとに id の付け方が割れ、後で直すと承認が戻る |
| サーバー側で画面を作る webapp の書き方 | 画面のひな形はフレームにしない。受け口の前後に動く処理 (callback) は、その操作に掛かるものだけ。保存が動かす処理、後で動くジョブ、メールの書き方を、説明書きの節にまとめた | 実物 (Rails) で、3 件を分析して決めた。道具で取れた入口は 6 割で、残りは、枠組みの規約を読んで足した |
| 確認だけをする middleware は、終端にできる | 機械チェックの終端の決まりに、「権限の確認を持つ」を足した (どのプロファイルにも効く) | 実物で、確認だけの middleware が検査に落ち、同じ確認を業務のルールにも書いて回避していた |
| 権限の確認の値は、実行時に比べる値そのもの | 定数の名前ではなく、値を書く。どれか 1 つで通る確認は、権限ごとに 1 件 | 入口をまたいで、同じ権限が 1 つにまとまる |
| 画面と API が同じリポジトリにあるシステム | 分析リポジトリ 1 つ = プロファイル 1 つ。画面を通らない API も見たいときは、分析リポジトリを分ける | 入口の単位と層の連鎖が、プロファイルごとに違う |
