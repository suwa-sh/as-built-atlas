# `cli` の決まり

[← プロファイルの仕様へ](../profiles.md)

| 決まり | 内容 | 理由 |
|---|---|---|
| 層は、役割で分ける | command (入口) → logic (処理の手順と業務の決まり) → adapter (データや外部とのやり取りを包むコード) → external (外部のコマンド、ライブラリ) | 言語や、フォルダの分け方は、対象ごとに違う。対象のフォルダと層の対応は、分析リポジトリの `analysis-conventions.md` に書く |
| 層を分けていない道具では、logic と adapter を作らない | 入口のフレームから、直接 external を呼んでよい。どの層にも、読み書きを書ける | 小さなスクリプトに、無い層を当てはめない |
| 入口は、利用者が起動できる操作 1 つ | 実行ファイル 1 つ。サブコマンドがあれば、サブコマンド 1 つ。起動用の薄いスクリプト (本体を exec するだけ) は、入口のフレームにまとめる | 直すときの単位が、操作だから |
| 整形だけのコマンドと、ファイルを直接読み書きするコマンドは、フレームにしない | パイプの中の `jq`、`sed`、`awk`、`grep` は書かない。`cat`、`cp`、`mv`、`rm`、リダイレクトは、そのフレームの読み書きに書く。別のプロセスやサービスに届くコマンド (`psql`、`ssh`、`curl`) だけを external にする | 処理の段が、小さなコマンドで埋まる |
| 判定や計算だけの関数は、業務のルールを書けば、終端のフレームにできる | 機械チェックの終端の決まりに、「業務のルールを持つ」を足した (どのプロファイルにも効く。後に、「行き先の入口が分かっているつながり (`embed` / `trigger` と `entry_id`) を持つ」も足した) | 実物で試したとき、純粋な関数をフレームにできず、業務の決まりの層が処理の木から消えた |
| どれか 1 つだけ選べるオプション (モード) で処理が分かれる実行ファイルは、モードごとに入口にする | サブコマンドと同じ扱い | 実物で、オプションごとに読むファイルも処理も別だった |
| テーブルをキューとして使っていても、`rdb` のまま | 使い方は、状態の列に書く値 (`set_to`) と、データを介したつながりの表 (`mart_data_links`) で見る | データの種類は、置き場で決める (使い方では決めない) |
| 別の機械のコマンドの起動 (`ssh`) は、外部の呼び出し | 相手のコマンドが同じリポジトリにあっても、そこでは辿らず、つながり (`links`) に書く | 動く場所が別で、入口として別に分析できる |
| 終了コードの決まりは、業務のルールに書く | どの場合に、どの値で終わるか | 呼び出す側 (スケジューラ) との約束になる |
