# 入口の照合、一括の承認、差分からの更新のコマンド

[← 仕様の地図へ](README.md)

コマンド `code-map`、`propose`、`approve`、`queue`、`impact`、`reuse` の仕様です。
手順は、手引きの [初めて分析する](../guide/first-analysis.md) と [対象のコードが進んだら更新する](../guide/update-analysis.md) にあります。

| コマンド | すること | 節 |
|---|---|---|
| `code-map` | 固定コミットのファイルを並べ、入口の定義ファイルと入口を照合する | 入口の定義ファイルを先に確かめる |
| `propose`、`approve`、`queue` | 入口の採否と作業の案を作る、承認する、残りの作業を返す | 入口と作業を一度で承認する |
| `impact` | 対象の差分から、入口ごとの作業の一覧を出す | 作業一覧を出す |
| `reuse` | 入口 1 件の再利用を確定する | 今回の結果を確定する |

結果の読み方 (状態の値と、前の結果との差分) は、最後の「結果の状態と差分」にあります。

## 比べるもの

更新のコマンドは、前回と今回を、次の 2 つで比べます。

| 比べるもの | どこから取るか |
|---|---|
| 前回の入口一覧と結果 | 分析リポジトリのコミット (`--from <前回の分析コミット>`) |
| コードの差分 | 対象リポジトリ。入口ごとに、結果の `target.commit` から今回の作業定義のコミットまで |

## 入口の定義ファイルを先に確かめる (`code-map`)

作業定義の `target.commit` と `target.scope` が指す Git ツリーから、通常ファイルのパスを並べたコードマップを作ります。
入口一覧や分析結果を用意する前から使えます。
分析リポジトリで実行します。

```bash
docker compose run --rm abatlas code-map .
```

照合 (`--check`) は、定義ファイルの規則と、入口の拾い方 (入口一覧の抽出器の設定) を書いた後に使います。
入口一覧 (`analysis/entry-list.yaml`) が無いと、終了コード 2 で止まります。

```bash
docker compose run --rm abatlas code-map . --check
```

| 書き方 | 動き |
|---|---|
| `code-map .` | コードマップを作る |
| `code-map . --check` | 固定コミットから入口を再列挙し、各定義ファイルに対応する入口 ID を表示する。採否を決める前の候補や、列挙した後に却下した入口も数える |
| `--json` を付ける | ファイルの一覧、定義ファイルの集合を取得できる。照合のときは、ファイルごとの入口 ID と漏れたパスも取得できる |

### 定義ファイルの規則

各ファイルに入口の定義があると判断できる範囲は、作業定義に書けます。
たとえば、ことり書店では `flows/` 以下の YAML がすべて Flow の定義です。
抽出器の探索先を誤って `flows/daily/` に狭めても、この規則が月次の定義を拾います。

```yaml
analysis:
  entry_file_patterns: ['flows/.+\.ya?ml']
```

- 規則を省略した場合は、コードマップの作成と従来の作業案の作成ができます。`--check` には規則が必要です。
- 規則が不正、またはいずれかの式がファイルに一つも一致しなければ、規則を見直してください。

### 照合の結果

| 起きたこと | 終了コード | 出るもの |
|---|---|---|
| 再列挙に成功し、すべての定義ファイルに入口が対応した | 0 | ファイルごとの入口 ID |
| 再列挙に成功し、入口が一つも出ていない定義ファイルがある | 1 | 漏れたパス |
| 再列挙そのものが失敗した (例: 抽出器の探索先に定義が見つからない。対象範囲にサブモジュールや Git LFS 管理ファイルがある) | 2 | 標準エラーに原因。照合結果の JSON は出力できない |

- 作業案の作成と承認でも、同じ照合を行います。
- 照合の単位はファイルです。一つのファイルに複数のルートがあるときは、そのファイル内の登録も調べます。
- シンボリックリンクとサブモジュールは、通常ファイルの集合から除きます。

### ことり書店の公開見本で照合する

見本の `target.commit` は生成時の内容ハッシュです。
コードマップを試すときは、通常の見本の手順で checkout の外へコピーして初期化した `kotori-books-atlas/` で、隣の対象にも Git の版を作ります。

```bash
git -C ../kotori-books init
git -C ../kotori-books add .
git -C ../kotori-books commit -m "ことり書店の見本"
git -C ../kotori-books rev-parse HEAD
```

表示された SHA を、コピー側の `analysis/work-definition.yaml` と `analysis/entry-list.yaml` の `target.commit` に設定します。
`docker compose run --rm abatlas code-map . --check` で、定義ファイル 34 件と入口 ID の対応を確認できます。

## 入口と作業を一度で承認する (`propose`、`approve`、`queue`)

分析リポジトリで「今回の分析を進めて」と頼むと、配布スキル `abatlas-run-analysis` が案を作ります。
スキルは、次の順で進めます。

1. 入口の用途や影響先を調べる。
2. 判断が必要な点だけを、人にまとめて質問する。
3. 回答を反映した件数と理由を示す。
4. その案に対する承認を、一度受ける。

```bash
docker compose run --rm abatlas propose . --from <前回の分析コミット> --draft analysis/batch-draft.yaml
docker compose run --rm abatlas approve . --from <前回の分析コミット> --draft analysis/batch-draft.yaml --plan-id <表示されたID> --by <承認者>
docker compose run --rm abatlas queue . --plan-id <承認したID>
```

| コマンド | 動き |
|---|---|
| `propose` | 案を作る。読み取り専用。`--json` で、全入口、理由、共通の変更ファイルを取得できる |
| `approve` | 案を承認し、今回分の仕事を返す。再利用は、承認と同時に確定する |
| `queue` | 承認済みで、まだ終わっていない作業を返す。中断の後に使う。分析と再分析は、検査とレビューが済むまで残る。廃止は、現行の資産を外すまで残る |

初回は、`--from <前回の分析コミット>` を `--initial` に置き換えます。

### 下書き (`--draft`) に書くこと

| 項目 | 書くこと |
|---|---|
| `assessment` | AI が調べた根拠 |
| `decisions` | 入口を含める、外す、再分析する判断。対象の入口 ID (`entries`)、判断 (`action`)、理由 (`reason`) をまとめる |
| `questions` | 人への質問。対象の入口 ID とまとめる |

### 確定できる条件

- 未解決の質問や、採否を決めていない候補があると、確定できません。
- 選択した案や前提が変われば、新しい ID で確認します。
- 初回の途中で条件を変更したときは、同じ対象版で `--initial` の案を更新できます。途中まで保存した結果も、新しい条件で再分析します。

### 承認の後の進み方

1. 取りまとめ役が、分析対象を入口ごとの担当に渡す。
2. 大量の再分析では、共通差分の根拠を共有する。最初の 2〜3 件を確かめてから、残りを少数並列で進める。
3. 廃止対象では、旧版が Git 履歴に保全されていることを確認してから、現行の資産を外す。
4. 中断した後は、`queue` が返す作業から続ける。
5. 最後に `build` する。

## 作業一覧を出す (`impact`)

対象の差分から、入口ごとの作業と理由を出します。

### 実行の前にそろえるもの

1. 更新前の分析資産をコミットし、その版を控えます。対象 Git の新旧の版をローカルで読めるようにします。
2. 対象を今回のコミットで checkout し、作業定義と入口一覧の `target.commit` をその版に合わせます。

### 実行する

分析リポジトリで実行します。
人向けの一覧に加えて、`--json` でランナー用の JSON を出せます。

```bash
docker compose run --rm abatlas impact . --from <前回の分析コミット>
docker compose run --rm abatlas impact . --from <前回の分析コミット> --json
```

- ツールは、今回のコミットを一時ディレクトリに展開し、入口を全件列挙します。
- 一覧と結果は書き換えません。
- プロファイル、分析規約、入口の承認、リンク先、入口を包む関係も確認します。

### 出る作業

| 作業 | 理由 | 次に行うこと |
|---|---|---|
| 承認待ち・追加分析 | 新しい候補、または承認済みで結果が無い | 列挙と承認を済ませ、分析する |
| 再分析 | 前回の定義場所や主張の根拠が変更・移動・削除された、または分析条件が変わった | ファイル差分と表示された呼び出し経路を読む |
| 廃止確認 | 前回の入口が列挙から消えた、または結果のある入口を却下した | リンク元を確かめる。人の確認後に旧資産を Git 履歴に保全し、現行の結果・レビュー・再利用記録から外す |
| 再利用候補 | 記録されている根拠と分析条件が同じ | 未記録の影響を確認して、入口ごとに確定する |

影響一覧はファイル単位です。
コードの変更内容と各入口の挙動は、分析担当者が差分を読んで判断します。

| ことり書店での例 | 出るもの |
|---|---|
| 共通ランナーが変わる | 同じファイルを参照する 32 入口に、共通の理由が付く |
| 決済処理が変わる | 決済と日締めの 2 入口に、呼び出し経路が出る |

## 今回の結果を確定する (`reuse`)

一括の承認 (上の `approve`) を使ったときは、再利用は承認と同時に確定しています。
この節は、一括の承認を使わずに、入口ごとに再利用を確定するときの仕様です。
確定した後の結果の読み方は、下の「結果の状態と差分」にあります。
一括の承認で進める手順は、手引きの [対象のコードが進んだら更新する](../guide/update-analysis.md) にあります。

### 入口ごとに進めること

再分析する入口と、再利用する入口の両方を含む、今回の更新の全体の進め方です。

- `enumerate` で今回の一覧を保存し、入口を承認します。承認後に `impact` で一覧を作り直します。
- 共通処理の実装差分を一度読み、今回の版と根拠行を控えます。各入口では、呼び出し元の設定と引数、終了条件、後続処理への伝わり方を調べます。再分析した入口の分析結果は、入口ごとの完全な YAML を保存します。再利用する入口の結果は、書き換えません (書き換えると、再利用の候補から外れます)。確認した理由は、下の `--reason` に渡します。
- 変更ファイルの一覧から、新しい登録規則、動的な呼び出し、追加テストが、他の入口に影響しないかを確認します。影響範囲を特定できないときは、その範囲を再分析します。入口を特定できなければ、全件を対象にします。

### 実行する

```bash
docker compose run --rm abatlas reuse . --from <前回の分析コミット> \
  --plan-id <impactの計画ID> --entry daily.db_snapshot \
  --by <確認者> --reason '変更のあった起動スクリプトを通らず、追加された呼び出しも無い'
```

| 指定 | 内容 |
|---|---|
| `--plan-id` | `impact` が出した計画 ID |
| `--entry` | 再利用する入口 |
| `--by` | 確認者 |
| `--reason` | 人が判断した理由 |

- 対象は、作業定義の版と一致する clean checkout を使います。Git が無視する生成物は、判定から除きます。
- 確認記録は、`analysis/reuse/` に入口ごとに残ります。
- 判定が変わると、計画 ID が変わります。最新の一覧で確認をやり直してください。
- 再利用を確定する操作は、入力が同じほかの候補の計画 ID を維持します。

## 結果の状態と差分

一括の承認で確定した再利用にも、入口ごとに確定した再利用にも、当てはまります。

`validate result --work` と `build` は、元結果、入口、分析条件と、対象 Git の新旧の根拠ファイルを照合します。

### 入口の概要の項目

| 項目 | 値 | 意味 |
|---|---|---|
| `target_commit` | コミット | 実際に分析した版 |
| `effective_commit` | コミット | 利用できる版 |
| `update_status` | `analyzed` | 分析した |
| `update_status` | `reused` | 再利用した |
| `update_status` | `stale` | 対象 (リポジトリ、範囲、コミット) が作業定義と違い、再利用も確定していない結果。`effective_commit` は空になり、`target_commit` だけが残る |

結果がまだ無い入口では、3 つの項目とも値がありません (null)。

### 進捗の項目

次の 3 項目は、承認済みの入口だけを数えます。

| 項目 | 意味 |
|---|---|
| `analyzed` | 結果がある入口の数 |
| `current_results` | 今回有効な数 (`update_status` が `analyzed` か `reused` の結果の数) |
| `reused_results` | 今回有効な数のうち、再利用した数 |

- 対象の版を変えずに分析条件だけを変えたときは、再分析が要る結果も `current_results` に入ります。残りの作業は、`impact` の一覧で確かめます。
- 残りのコストと時間は、承認済みで今回有効な結果がない入口の件数から見積もります。
- 元の結果、分析日時、レビューを、再利用で上書きすることはありません。

### 集計の後の差分

- 集計後の `diff . --from <前回の分析コミット>` は、以前と同じく、入口ごとの分析内容の変化を出します。
- 次の更新も、元の分析コミットと直接比べます。
- 各結果を保存した分析コミットの規約と、入口の境界も照合します。
- 保存時点を確認できない場合は、再分析します。
